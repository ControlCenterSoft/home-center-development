# Home Center 0.59.0

**Статус:** активная подготовка разработки; не Release Candidate и не Public Stable.

## Цель релиза

0.59.0 вводит первый Policy Composer для интерфейса «Уютный»: роль члена семьи преобразуется в проверяемый `PolicyBundle`, показывается понятным бытовым объяснением и после отдельного подтверждения может быть материализована в защищённое локальное Desired State. Точная техническая форма той же политики остаётся доступной «Полному» интерфейсу.

## Подготовленная граница

На текущем этапе подготовлены доменные контракты, durable plan/confirm runtime, единая модель представления для «Уютного»/«Полного» интерфейсов, production HTTP-boundary, audit-bound история ревизий и защищённая локальная материализация/rollback Policy Desired State без provider/infrastructure execution:

- детерминированный `PolicyBundle`, построенный из текущего `RolePreset` / `EffectivePolicy`;
- единый exact-state presentation model: «Уютный» получает короткое бытовое объяснение и явную кнопку подтверждения, «Полный» — тот же `bundle_id`, технический policy payload и evidence/revision;
- стабильный `desired_state_resource_key` для защищённой записи;
- confirmation-gated proposal, привязанный к точным `snapshot_id`, `resource_version` и `generation` Household;
- proposal также привязан к точной ранее наблюдавшейся ревизии Policy Desired State: `expected_desired_state_generation` и `expected_desired_state_bundle_id`; эта optimistic concurrency граница не позволяет тихо перезаписать более новую policy revision;
- повторная проверка полномочий родителя/администратора, Household snapshot и Desired State precondition перед подтверждением и перед записью;
- durable хранение plan/confirmation evidence в локальном StateStore;
- идемпотентный replay уже подтверждённого proposal без повторного confirmation Audit;
- fail-closed промежуточное состояние `confirming`: после прерывания подтверждение нельзя автоматически считать успешным;
- явный confirmation recovery возвращает неизменившийся proposal в `pending`, а stale/повреждённый proposal переводит в `invalidated`;
- отдельный Desired State writer принимает только exact confirmation receipt и делает SQLite compare-and-set по ожидаемой generation/bundle revision;
- write protocol фиксирует `applying` marker, pre-write Audit, CAS-write, completion Audit и durable apply receipt;
- неоднозначное прерывание после фактической записи распознаётся по exact target bundle и завершается как recovery без повторной мутации;
- повторная материализация уже идентичной политики является честным no-op и не увеличивает generation;
- Policy Desired State хранит только описательную политику и не выдаёт provider execution, infrastructure mutation или external publication authority;
- каждая наблюдаемая Policy Desired State revision архивируется по `(resource_key, generation)` с SHA-256 evidence и отдельной записью в keyed append-only Audit chain;
- чтение history fail-closed проверяет payload hash, `bundle_id` и соответствующее Audit evidence после проверки целостности Audit chain;
- explicit rollback принимает только точную текущую `generation`/`bundle_id`, старую подтверждённую history generation и `confirmed=true`;
- rollback не откатывает счётчик поколений назад: старая policy materializes как новая monotonic generation;
- rollback имеет durable `applying/applied/invalidated` state, идемпотентный replay и recovery после неоднозначного прерывания записи;
- stale current revision, повреждённая history/evidence, чужой Household и actor без административных полномочий отклоняются fail-closed;
- runtime composition root создаёт Policy plan/confirm service, защищённый Desired State writer, history/rollback service и общий workflow orchestration service как один production-контур;
- production web server использует отдельный policy HTTP-handler поверх существующего V2 handler и наследует общие request classification, authentication, password-change и same-origin ограничения;
- policy HTTP boundary дополнительно **явно отклоняет все externally classified requests**, даже если внешний доступ к другим частям Home Center включён;
- persisted-state/evidence integrity failures в policy HTTP boundary классифицируются как `503 Service Unavailable`, а не как пользовательская ошибка `400`, чтобы повреждение локального состояния не маскировалось под некорректный запрос;
- подготовлены POST-boundaries `/api/v1/household/policies/plan`, `/confirm`, `/recover` и `/rollback`; ни один из них не выдаёт provider execution authority;
- «Уютный» интерфейс получил карточку настройки правил семьи: выбор человека, безопасный preview, бытовое объяснение и отдельную кнопку «Применить правила»;
- «Полный» интерфейс получает exact-state inspector того же плана с тем же `proposal_id`, `bundle_id`, revision/evidence и technical policy payload;
- web-клиент выводит серверные значения только через `textContent`, не использует HTML-injection path и не вызывает provider/execution/jobs endpoints;
- добавлены закрытые JSON contracts для plan/confirm/recovery request, recovery result, plan result, shared Cozy/Full presentation, confirmation/apply result, history evidence и rollback request/receipt;
- confirmation contract согласован с идемпотентным replay: явно допускаются только `confirmed-for-desired-state-write` и безопасный `already-confirmed`, без расширения mutation authority;
- существующий `household-policy-apply-receipt.v1` сохранён закрытым: history metadata вынесены на уровень workflow result и не добавляются в apply receipt;
- подготовлен backup/restore source-test: Household, confirmation/apply envelopes, Policy Desired State и Audit chain должны переживать SQLite backup/restore, а повторный apply после восстановления обязан быть идемпотентным;
- подготовлены negative/stale/replay/recovery/no-op/presentation/backup-restore/runtime-workflow/web-source/history/rollback, HTTP failure-classification и closed-contract тесты исходного кода; в этом non-runner потоке они намеренно не запускались.

## Границы безопасности

Подготовленная часть 0.59.0:

- меняет только локальное Policy Desired State после exact explicit confirmation;
- не создаёт provider execution Job и не вызывает provider/adapter;
- не применяет сетевые, VPN, storage, account или device-management изменения;
- не включает внешнюю публикацию policy API;
- не выдаёт полномочия на production infrastructure mutation;
- отклоняет stale proposal при изменении Household snapshot или ранее наблюдавшейся Policy Desired State revision;
- не позволяет child/guest инициировать административную policy-композицию или rollback;
- confirmation receipt сам по себе не является полномочием на произвольную запись: writer повторно связывает actor, proposal, confirmation и exact CAS precondition;
- production HTTP write-path остаётся authenticated, same-origin и internal-only для policy routes;
- «Уютный» и «Полный» представляют одну и ту же policy evidence и не имеют отдельных обходных mutation-path;
- history payload связан с keyed Audit evidence, поэтому простая подмена history hash/payload без нарушения Audit evidence отклоняется;
- rollback требует explicit confirmation и exact current-state precondition и никогда не вызывает provider execution;
- после неоднозначного прерывания запись либо доказывается exact-state evidence и финализируется, либо остаётся fail-closed/invalidated.

Подробные правила parental/proxy filtering, quota и расписаний относятся к последующим релизным границам и здесь не реализуются. Аналогично provider-specific VPN и account/profile provisioning не входят в 0.59.0.

## Что требуется до Release Candidate

До присвоения 0.59.0 статуса Release Candidate необходимо как минимум:

1. выполнить runner-зависимую qualification уже подключённых production API/UI/history/rollback boundaries и runtime workflow tests, включая реальные HTTP auth/same-origin/external-deny/password-change сценарии; этот non-runner поток CI не запускал;
2. расширить qualification аварийных точек rollback/write protocol, включая процессное прерывание между Audit/Desired State/history/state-marker операциями и повреждение persisted evidence;
3. runner-потоком фактически подтвердить подготовленный single-node restart и backup/restore path, включая history/Audit/rollback state, затем добавить поддерживаемый HA/restart qualification;
4. подтвердить install/upgrade с сохранением Household, Policy Desired State, history, confirmation/apply/rollback envelopes, пользовательских настроек и локальной аутентификации;
5. подтвердить schema validation новых закрытых contracts на фактических API responses, включая idempotent replay и confirmation recovery;
6. после закрытия qualification выполнить штатную release-подготовку и публикацию только соответствующим runner/release-потоком.

До закрытия этих пунктов наличие исходного кода 0.59.0 не означает доступность capability в Stable.
