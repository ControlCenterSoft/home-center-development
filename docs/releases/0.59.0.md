# Home Center 0.59.0

**Статус:** активная подготовка разработки; не Release Candidate и не Public Stable.

## Цель релиза

0.59.0 вводит первый Policy Composer для интерфейса «Уютный»: роль члена семьи должна преобразовываться в проверяемый PolicyBundle и далее, после отдельного подтверждения, в защищённое Desired State. Техническая форма политики остаётся доступной «Полному» интерфейсу, а бытовой интерфейс получает понятное объяснение итоговой EffectivePolicy.

## Подготовленная граница

На текущем этапе подготовлены доменные контракты и отдельный durable plan/confirm runtime без записи PolicyBundle в Desired State и без инфраструктурного выполнения:

- детерминированный `PolicyBundle`, построенный из текущего `RolePreset` / `EffectivePolicy`;
- точный технический policy payload для «Полного» интерфейса;
- краткое русскоязычное объяснение итоговой политики для «Уютного»;
- стабильный `desired_state_resource_key` для будущей защищённой записи;
- confirmation-gated proposal, привязанный к точным `snapshot_id`, `resource_version` и `generation` Household;
- proposal также привязан к точной ранее наблюдавшейся ревизии Policy Desired State: `expected_desired_state_generation` и `expected_desired_state_bundle_id`;
- повторная проверка полномочий родителя/администратора, Household snapshot и Desired State precondition перед подтверждением;
- durable хранение plan/confirmation evidence в локальном StateStore;
- идемпотентный replay уже подтверждённого proposal без повторного confirmation Audit;
- fail-closed промежуточное состояние `confirming`: после прерывания подтверждение нельзя автоматически считать успешным;
- явный recovery возвращает неизменившийся proposal в `pending`, а stale/повреждённый proposal переводит в `invalidated`;
- confirmation receipt означает только готовность точного proposal к следующей защищённой операции записи; сам receipt не выдаёт `desired_state_write_authorized`, infrastructure mutation или external publication authority;
- подготовлены negative/stale/replay/recovery тесты исходного кода; в этом non-runner потоке они намеренно не запускались.

## Границы безопасности

Подготовленная часть 0.59.0:

- пока не меняет Policy Desired State;
- не создаёт execution Job;
- не вызывает provider/adapter;
- не применяет сетевые, VPN, storage, account или device-management изменения;
- не включает внешнюю публикацию;
- не выдаёт полномочия на production mutation;
- отклоняет stale proposal при изменении Household snapshot или ранее наблюдавшейся Policy Desired State revision;
- не позволяет child/guest инициировать административную policy-композицию;
- после неоднозначного прерывания подтверждения требует fail-closed recovery и повторное явное подтверждение.

Подробные правила parental/proxy filtering, quota и расписаний относятся к последующим релизным границам и здесь не реализуются. Аналогично provider-specific VPN и account/profile provisioning не входят в 0.59.0.

## Что требуется до Release Candidate

До присвоения 0.59.0 статуса Release Candidate необходимо как минимум:

1. реализовать защищённую запись PolicyBundle в Desired State с optimistic concurrency, потребляющую exact confirmation receipt;
2. добавить обязательный Audit до/после фактического Desired State write и recovery semantics для прерванной записи;
3. связать представление PolicyBundle с «Уютным» и «Полным» интерфейсами без обхода общих Identity/RBAC gates;
4. определить rollback/forward-recovery для уже записанной policy materialization;
5. расширить negative/security/stale/replay qualification на сам Desired State writer;
6. подтвердить single-node и поддерживаемый HA/restart path;
7. подтвердить install/upgrade с сохранением Household, пользовательских настроек и локальной аутентификации;
8. запустить штатную runner-зависимую qualification только в соответствующем release-потоке и после этого пройти публикацию.

До закрытия этих пунктов наличие исходного кода 0.59.0 не означает доступность capability в Stable.
