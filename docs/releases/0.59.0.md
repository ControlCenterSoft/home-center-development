# Home Center 0.59.0

**Статус:** ранняя подготовка разработки; не Release Candidate и не Public Stable.

## Цель релиза

0.59.0 вводит первый Policy Composer для интерфейса «Уютный»: роль члена семьи должна преобразовываться в проверяемый PolicyBundle и далее, после отдельного подтверждения, в защищённое Desired State. Техническая форма политики остаётся доступной «Полному» интерфейсу, а бытовой интерфейс получает понятное объяснение итоговой EffectivePolicy.

## Подготовленная foundation-граница

На текущем этапе подготовлены только чистые доменные контракты без записи состояния и без инфраструктурного выполнения:

- детерминированный `PolicyBundle`, построенный из текущего `RolePreset` / `EffectivePolicy`;
- точный технический policy payload для «Полного» интерфейса;
- краткое русскоязычное объяснение итоговой политики для «Уютного»;
- стабильный `desired_state_resource_key` для будущей защищённой записи;
- confirmation-gated proposal, привязанный к точным `snapshot_id`, `resource_version` и `generation` Household;
- повторная проверка полномочий родителя/администратора и exact-state перед будущим подтверждением;
- default-deny для записи Desired State, инфраструктурных изменений и внешней публикации на стадии plan/proposal.

## Границы безопасности

Подготовленная часть 0.59.0:

- не меняет Desired State;
- не создаёт Job;
- не вызывает provider/adapter;
- не применяет сетевые, VPN, storage, account или device-management изменения;
- не включает внешнюю публикацию;
- не выдаёт полномочия на production mutation;
- отклоняет stale proposal при изменении Household snapshot;
- не позволяет child/guest инициировать административную policy-композицию.

Подробные правила parental/proxy filtering, quota и расписаний относятся к последующим релизным границам и здесь не реализуются. Аналогично provider-specific VPN и account/profile provisioning не входят в 0.59.0.

## Что требуется до Release Candidate

До присвоения 0.59.0 статуса Release Candidate необходимо как минимум:

1. реализовать durable plan/confirm runtime и idempotency;
2. реализовать защищённую запись PolicyBundle в Desired State с optimistic concurrency;
3. добавить обязательный Audit до/после подтверждённого изменения и recovery semantics для прерванной записи;
4. связать представление PolicyBundle с «Уютным» и «Полным» интерфейсами без обхода общих Identity/RBAC gates;
5. определить rollback/forward-recovery для policy materialization;
6. добавить negative/security/stale/replay qualification;
7. подтвердить single-node и поддерживаемый HA/restart path;
8. подтвердить install/upgrade с сохранением Household, пользовательских настроек и локальной аутентификации;
9. пройти штатную release qualification и публикацию.

До закрытия этих пунктов наличие исходного кода 0.59.0 не означает доступность capability в Stable.
