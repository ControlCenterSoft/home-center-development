# Home Center 0.59.0

Status: official release.

## Профиль релиза

Home Center 0.59.0 — bounded technical release поверх официального Public Stable 0.58.0. Релиз добавляет Policy Composer и безопасный lifecycle применения household policy: защищённый Desired State, read-only Actual/effective state, confirmation-gated enforcement, точную backend qualification binding, read-only reconciliation и отдельный verified-state transition без ложного Success.

Заявленный технический профиль релиза — `single-node-core`. Multi-node HA / automatic failover, универсальная concrete production backend/provider execution и commercial launch clearance не заявляются как квалифицированные возможности 0.59.0 без отдельного exact-bound evidence. Неподтверждённые возможности остаются fail-closed, disabled или unclaimed; отсутствие evidence не превращается в фиктивный PASS.

## Что добавлено

- PolicyBundle / ComposedPolicy поверх Household RolePreset с anti-escalation semantics: policy может только ужесточать разрешённый role baseline и не получает скрытой external-publication authority;
- exact-state policy plan → explicit confirm → protected Desired State commit с server-side Household parent/admin authority, stale-state rejection, durable Job/Audit/evidence и идемпотентностью;
- понятная проекция policy для «Уютного» и точная техническая проекция для «Полного» интерфейса без заявления неподтверждённого enforcement success;
- read-only effective-state и reconciliation boundary с deliberately registered read-only adapters, точной Desired State/policy/evidence binding и fail-closed обработкой stale/tampered/ambiguous observation;
- restart-safe recovery уже сохранённого reconciliation evidence без повторного backend invocation;
- protected verified policy-state projection и отдельный reconciliation-to-verified transition после fresh server-side authority/Desired State revalidation;
- confirmation-gated policy enforcement plan/confirm/execute path, где mutation-capable backend допускается только при deliberately registered capability и exact backend qualification evidence;
- policy-backend qualification contract связывает backend id/version, candidate artifact, environment и execution transcript SHA-256 с точной release identity;
- enforcement admission повторно проверяет current actor authority, scoped re-auth, exact current Desired State, backend registration/capabilities и exact qualification evidence непосредственно перед execution;
- backend acceptance не означает enforcement success: post-condition reconciliation остаётся обязательной отдельной границей;
- automatic retry/reinvocation после ambiguous outcome запрещён; reconciliation остаётся read-only и не повторяет provider/backend mutation;
- node deployment artifact и reproducible wheel qualification требуют полный inherited 0.58 runtime и текущие 0.59 policy/enforcement/reconciliation/verification modules; deployment MANIFEST связывает runtime, contracts и policy UI exact SHA-256;
- bounded target-node qualification и `single-node-core` technical Stable gate требуют exact candidate identity, reproducibility, security, upgrade/rollback/state preservation, real target-node evidence и полный immutable release artifact set.

## False-success boundary

Сохранённый Desired State, принятая backend-команда и даже корректно сохранённое reconciliation evidence не являются сами по себе подтверждённым enforcement success. Verified state допустим только после exact-bound read-only observation/reconciliation, повторной проверки текущего Desired State/authority и отдельного durable verification transition.

Unknown, ambiguous, stale, future-dated, mismatched, incomplete или tampered evidence работает fail-closed. Automatic backend retry после неоднозначного результата запрещён.

## Безопасность

- Identity/RBAC, same-origin/CSRF, scoped re-auth и exact-state binding применяются на risk-bearing HTTP boundaries;
- secret values не входят в public policy/release evidence contracts;
- backend/provider payload не становится generic command API;
- infrastructure/network/filesystem mutation и external publication не выдаются Policy Composer автоматически;
- CodeQL `security-extended`, public repository privacy boundary и infrastructure neutrality являются обязательными exact-candidate gates;
- reviewed CodeQL exceptions остаются привязаны к точным rule/path/line/source statements и при source drift должны fail-closed потребовать повторной проверки;
- release/promotion evidence не переносится между разными candidate revision/artifact identities.

## Upgrade / rollback

Поддерживаемая release boundary: официальный Public Stable 0.58.0 → 0.59.0. Exact candidate должен пройти clean packaging, reproducible wheel/node artifact qualification, checksum verification, install/upgrade, service health/restart, user-state/config/admin credential preservation и rollback/forward-recovery qualification на точной candidate identity.

Candidate identity не переписывается внутри тестов: `VERSION`, package metadata, runtime `__version__`, UI и deployment artifact обязаны совпадать с 0.59.0. Официальный 0.58.0 используется как immutable baseline для upgrade/rollback rehearsal.

## Явно не заявлено

- multi-node HA / automatic failover — не заявлены как квалифицированные в bounded `single-node-core` профиле 0.59.0;
- universal concrete production backend/provider execution — не заявляется без отдельно квалифицированного backend/adapter exact evidence;
- commercial launch clearance — отдельный коммерческий контур и не заявляется этим техническим релизом;
- arbitrary shell/command execution, automatic infrastructure mutation и implicit external publication не входят в scope 0.59.0.

Эти ограничения не маскируются как PASS. Пользовательский продукт может быть опубликован как bounded technical Public Stable только после успешной exact-candidate qualification обязательных технических gates и отдельного Public Stable promotion cycle.
