# Home Center 0.57.0

**Статус:** разработка и квалификация; не Release Candidate и не Public Stable.

## Цель релиза

0.57.0 вводит безопасную границу фактического запуска подключения домашнего устройства через выбранного провайдера управления устройствами. Релиз продолжает подтверждённый выбор провайдера из 0.56.0 и не расширяет полномочия автоматически.

## Реализуемая граница

- отдельный план выполнения с неизменяемой привязкой к семье, устройству, пользователю, снимку состояния, каталогу и выбранному провайдеру;
- отдельное явное подтверждение перед первым обращением к провайдеру;
- типизированный provider-adapter boundary;
- в adapter передаются только ссылки вида `secret://...`, а не значения паролей, токенов или других секретов;
- ограниченный timeout выполнения;
- durable Job и Audit для start/cancel/retry;
- идемпотентное повторение одного и того же запроса без повторной отправки команды провайдеру;
- retry разрешён только когда adapter доказал, что предыдущая неудача произошла до принятия команды провайдером;
- timeout и неоднозначная транспортная ошибка считаются небезопасными для автоматического retry;
- cancel является отдельной явно подтверждаемой операцией и считается принятой провайдером только после корректного типизированного ответа; пустой, неполный или противоречивый ответ отклоняется fail-closed;
- одноразовый token/QR может быть представлен только ограниченной ссылкой на секрет с временем жизни и признаком single-use;
- незарегистрированный или неполный provider adapter отклоняется до начала исполнения.

## Важная семантика безопасности

Принятие команды внешним провайдером **не означает**, что устройство успешно подключено или стало управляемым. В 0.57.0:

- `enrollment_completed = false`;
- `post_condition_verified = false`;
- `managed_state_change_authorized = false`;
- применение политик не разрешается автоматически;
- изменение инфраструктуры и внешняя публикация не разрешаются автоматически.

Состояние `managed=true` допустимо только после отдельной последующей проверки фактического результата подключения. Эта проверка не входит в границу 0.57.0.

## API-контракты

Подготовлены закрытые схемы запросов и результатов для:

- `POST /api/v1/household/devices/enrollment/execution/plan`;
- `POST /api/v1/household/devices/enrollment/execution/start`;
- `POST /api/v1/household/devices/enrollment/execution/cancel`;
- `POST /api/v1/household/devices/enrollment/execution/retry`.

Неизвестные поля отклоняются. План и подтверждение проверяются повторно непосредственно перед выполнением.

## Совместимость single-node / HA

Модель хранит durable Job, Audit и execution evidence в штатном состоянии Home Center и не вводит отдельного обязательного внешнего координатора. Она не меняет действующую модель single-writer и не включает автоматический failover. При смене актуального Household snapshot, каталога провайдеров или выбранного провайдера выполнение блокируется как stale.

## Уже подтверждено квалификацией

- закрытые контракты, stale/replay/idempotency и отрицательные security-сценарии;
- воспроизводимая упаковка обязательных runtime-модулей;
- проверка перехода с опубликованного Stable 0.56.0 на кандидат 0.57.0 и обратного rollback с контролем checksum и release identity;
- сохранность конфигурации, SQLite state, rollback point и локальных учётных данных при проверочном upgrade/restart цикле;
- backup/restore durable execution state и Job evidence;
- запуск HTTPS runtime, `/readyz` и повторный запуск с тем же сохранённым состоянием;
- детерминированный порядок retry при совпадении времени создания попыток;
- fail-closed обработка неоднозначного provider start, некорректного cancel-result и отсутствующего provider adapter;
- отсутствие пути, который выставляет `managed=true` только на основании принятия команды провайдером.

## Что ещё требуется до Release Candidate

До присвоения статуса Release Candidate остаются содержательные проверки, которые нельзя подменять моделированием окружения:

1. service-level install/upgrade acceptance на квалифицированном тестовом узле с фактическим health и подтверждением сохранности пользовательского состояния;
2. расширенная HA/restart qualification на реальном multi-node контуре;
3. qualification конкретного provider adapter; без зарегистрированного adapter команда start должна завершаться fail-closed.

До закрытия этих пунктов документ не является заявлением о готовности 0.57.0 к эксплуатации.
