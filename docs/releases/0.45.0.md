# Home Center 0.45.0

Status: official release

## Scope

Home Center 0.45.0 adds the canonical multi-service requirement-set boundary from the approved roadmap: one module can deterministically require multiple Home Services without granting installation or execution authority.

`home-center.module-home-service-contract-multi-requirement-set.v1` combines existing exact `mhscr-*` single-service requirement sets into one deterministic `mhsmr-*` evidence object. The aggregate preserves each service identifier, exact single-service requirement-set identity and exact versioned Home Service/API contracts.

Input order does not affect identity: service requirements are canonicalized by service identifier. Duplicate service requirements, mixed Home Center/module contexts, malformed or tampered nested identities, non-canonical serialized order, mapping-subclass ambiguity and authority-bearing evidence are rejected fail-closed. Lazy aggregate input is bounded to 64 service requirement sets and iterator failures are normalized to a stable rejection code.

## Safety boundary

The aggregate is evidence only. It never authorizes admission, installation, execution, production mutation or external publication.

The contract is topology-neutral and infrastructure-neutral. It adds no Jobs/Operations behavior, Cluster/HA orchestration, placement semantics or release-promotion logic. Existing authentication policy is unchanged.

No persistent-state migration is required.

## Security and commercial boundary

The serialized contract is closed (`additionalProperties: false`), authority flags are fixed to `false`, nested exact identities are rebuilt and verified, and canonical ordering is enforced before an aggregate identity is accepted.

This version does not add a new third-party component or distribution mode. It therefore introduces no new license payload; existing module/service legal-compliance evidence remains authoritative for the referenced components.

## Release qualification

The exact release head must pass repository-wide CI, reproducible artifact qualification, public-repository privacy boundary and infrastructure-neutrality gates before merge, tag or publication. Publication does not grant production mutation authority; installation and activation remain governed by the normal verified update path.
