# Home Center 0.49.0

Status: official release.

## Кратко

Home Center 0.49.0 развивает две независимые и совместимые границы поверх 0.48.0:

1. точную повторную проверку агрегированной совместимости модулей сразу для нескольких Home Services;
2. подтверждаемое добавление членов семьи с ролями `parent`, `child` и `guest` из mobile-first интерфейса «Уютный → Семья».

Обе возможности реализованы fail-closed и остаются инфраструктурно нейтральными. Они не дают неявного права на выполнение provider-операций, изменение сети/инфраструктуры или внешнюю публикацию сервисов.

## Агрегированная совместимость модулей

Добавлен контракт `home-center.module-home-service-contract-multi-compatibility-binding-revalidation.v1`. Он проверяет исходное агрегированное доказательство совместимости, заново вычисляет состояние по актуальному набору требований, module-admission binding и профилям Home Services и детерминированно возвращает состояние `current` или `stale`.

Проверяются идентичность requirement set, версия Home Center, идентичность и версия модуля, набор сервисов, доказательства совместимости по каждому сервису, перечень заблокированных сервисов и итоговое агрегированное состояние. Повреждённые или внутренне противоречивые доказательства отклоняются до использования.

Контур остаётся evidence-only: admission, установка, исполнение, production mutation и внешняя публикация этим доказательством не разрешаются.

## Подтверждаемое изменение состава семьи

«Уютный → Семья» использует двухэтапную модель:

`план изменения → проверка имени/роли/исходной версии → явное подтверждение`

Планирование само по себе не изменяет Household state. Предложение связано с точными `snapshot_id`, `resource_version` и generation, существовавшими при его создании. Действующий член семьи определяется сервером из привязки аутентифицированного пользователя; клиент не может подменить actor/member identity для обхода политики.

Подтверждение принимается только если одновременно выполняются условия:

- пользователь всё ещё привязан к активному `parent` с правом администрирования;
- доказательство предложения целостно и соответствует серверному формату;
- текущие snapshot/resource version совпадают с базой предложения;
- добавляемый member ещё не существует;
- клиент явно отправил `confirmed=true`.

Если состояние семьи изменилось после планирования, операция отклоняется как устаревшая без изменения данных. Повтор подтверждения уже выполненного предложения возвращает записанный результат и не создаёт дубликат.

Household snapshot и commit дополнительно валидируются на границе value-object. Несогласованные `snapshot_id`, `resource_version`, `commit_id`, generation и previous-resource relation отклоняются fail-closed.

Применённое изменение ограничено внутренним Household product state. Оно не создаёт системные или доменные учётные записи, не изменяет профили, DNS, VPN, MDM, устройства или внешний Desired State, не запускает providers и не включает NAT/port-forwarding/внешнюю публикацию.

## Интерфейс «Уютный»

Сохранены существующие безопасные свойства 0.48: постоянное переключение `Уютный ↔ Полный`, клавиатурная tab-семантика, fail-closed отображение неизвестного состояния узлов и обязательная смена первоначального пароля до обычной работы.

В разделе «Семья» вместо неактивной заглушки появился отдельный поток добавления человека: ввод имени и роли, получение плана, просмотр предлагаемого изменения и отдельная кнопка подтверждения. UI-логика добавлена изолированным progressive-enhancement слоем, поэтому существующая accessibility/fail-safe логика основного интерфейса не заменяется.

## Безопасность и коммерческая граница

Релиз сохраняет серверную аутентификацию и actor/member boundary, same-origin проверку изменяющих HTTP-запросов, optimistic stale-state protection, детерминированные evidence-объекты, idempotent replay, audit chain и default-deny для внешней публикации.

Существующие контуры module legal/commercial compliance и их fail-closed проверки сохранены без ослабления. Новые функции 0.49 не предоставляют самостоятельного коммерческого разрешения модулю и не обходят существующий admission/legal-compliance pipeline.

## Установка и обновление

Переход с 0.48.0 на 0.49.0 выполняется штатным поддерживаемым upgrade-путём Home Center. Пользовательские данные, установленный пароль администратора и существующий Household state не должны сбрасываться при обновлении. Для HA-контура применяется обычный безопасный rolling-порядок с проверкой состояния между узлами и возможностью rollback.

Автоматическое обновление должно использовать только подтверждённый Public Stable канал. Официальная source-публикация и Public Stable promotion являются отдельными защищёнными этапами и должны сохранять одну и ту же квалифицированную идентичность релиза.

## Квалификация релиза

Точный source revision 0.49.0 должен пройти полный GitHub-hosted CI для Python 3.12/3.13, полный pytest, воспроизводимую сборку wheel, проверку обязательного состава runtime-артефакта, public-repository privacy boundary и infrastructure-neutrality. Публикация выполняется только из exact main revision, прошедшего эти gates.

Артефакт 0.49.0 обязан содержать оба runtime-направления релиза: агрегированную multi-service compatibility revalidation и полный Household member plan/confirm runtime. Public Stable promotion допускается только после успешной официальной публикации того же квалифицированного release identity.
