# Home Center 0.49.0

Status: source package ready for qualification.

## Scope

Home Center 0.49.0 combines two independent, cumulative boundaries on top of 0.48.0:

1. exact-state revalidation for aggregate module compatibility across multiple Home Services;
2. explicitly confirmed addition of `parent`, `child` or `guest` members from the mobile-first «Уютный» interface.

Both boundaries remain infrastructure-neutral and fail closed. Neither grants implicit provider execution or external publication authority.

## Aggregate module compatibility revalidation

The new `home-center.module-home-service-contract-multi-compatibility-binding-revalidation.v1` contract reconstructs the original aggregate compatibility evidence, computes a fresh aggregate from the current multi-service requirement set, module-admission binding and Home Service profiles, and deterministically reports `current` or `stale`.

Drift is tracked for the exact requirement-set identity, Home Center version, module identity/version, service set, per-service compatibility evidence, blocked-service set and aggregate compatibility status. Malformed or tampered original/fresh evidence is rejected fail-closed.

The aggregate compatibility contract remains evidence only. Admission, installation, execution, production mutation and external publication authority remain false.

## Confirmed Household member changes

«Уютный → Семья» now provides a bounded two-step flow:

`plan member → review name/role/base generation → explicit confirm`

The plan does not mutate Household state. It is bound to the exact `snapshot_id`, `resource_version` and generation observed when the proposal was created. The server derives the acting family member from the authenticated actor binding; the client cannot nominate another actor/member identity to bypass household policy.

Confirmation is accepted only when all of the following remain true:

- the caller is still bound to an enabled `parent` with administration permission;
- the proposal evidence is intact and was issued by the server;
- the current Household snapshot/resource version still matches the proposal base;
- the requested target member does not already exist;
- the client explicitly sends confirmation rather than treating planning as execution.

A stale or tampered proposal is rejected before state mutation. Replaying an already completed confirmation returns the previously recorded result rather than creating a duplicate member.

Household snapshot evidence is additionally validated at the value-object boundary: manually constructed `snapshot_id` and `resource_version` values must match the canonical Household payload, generation and predecessor snapshot. Forged or internally inconsistent snapshot evidence therefore fails closed before it can be used for planning or confirmation.

Accepted changes are limited to Home Center Household product state. The flow records pre-apply and completion audit evidence. It does **not** create operating-system or directory accounts, configure profiles, DNS, VPN, MDM or devices, change external Desired State, invoke providers, or enable NAT/port-forwarding/external publication.

## User interface

The authenticated «Уютный» interface keeps the persistent `Уютный ↔ Полный` switch and the three top-level sections `Домой`, `Семья`, `Мой дом`. In `Семья`, a configured household can now open the add-person form, select `Родитель`, `Ребёнок` or `Гость`, inspect the generated proposal and perform a separate confirmation action.

Mandatory first-login password rotation remains ahead of all ordinary Household actions.

## Safety boundary

The 0.49 release preserves the 0.48 authentication and server-side actor/member boundary, optimistic stale-state protection, deterministic evidence, idempotent replay behavior, audit-chain integration and default-deny external publication.

No new provider execution authority is introduced by this release. No automatic network, DNS, VPN, MDM, account/profile or external-publication mutation is introduced.

## Qualification boundary

The release artifact must contain both aggregate module-compatibility runtime and the complete Household member-change runtime. Repository qualification covers Python 3.12/3.13, full pytest execution, deterministic/reproducible wheel qualification, public-repository privacy checks and infrastructure-neutrality checks.

The release remains a qualification candidate until those repository-wide gates pass on the exact 0.49 release candidate commit.
