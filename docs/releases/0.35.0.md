# Home Center 0.35.0

Status: development qualification candidate.

Home Center 0.35 adds a versioned compatibility-policy boundary for module
candidate-set admission. The package does not install modules, execute module
actions, mutate infrastructure, or publish services externally.

## Compatibility policy snapshot

`ModuleCompatibilityPolicySnapshot` creates a deterministic `mcp-*` identity for
one exact compatibility policy. The policy can define:

- explicitly blocked module IDs;
- an optional publisher allow-list;
- runtime capabilities required for any candidate set;
- a maximum number of candidates evaluated as one set;
- an explicit semantic policy version.

Policy inputs are normalized and duplicate values are rejected. Publisher
restriction is fail-closed: an enabled allow-list must contain at least one
publisher, while an unrestricted policy cannot carry ignored allow-list values.

The compatibility policy is separate from module artifact signature trust.
Artifact provenance, signing-key threshold, manifest binding, and content digest
remain verified by the existing module artifact boundary.

## Policy-bound candidate-set decision

`evaluate_module_candidate_set_under_policy()` first obtains the normal exact
candidate-set compatibility decision against the canonical runtime snapshot.
It then evaluates the exact policy snapshot without changing that base
compatibility evidence.

The returned `home-center.module-policy-candidate-set-decision.v1` binds:

- exact `mcp-*` policy identity and policy version;
- exact `mcsd-*` candidate-set decision;
- exact `mcs-*` runtime compatibility snapshot;
- base and policy-specific blocked-module sets;
- missing policy-required runtime capabilities;
- per-module publisher identity and policy rejection reasons.

A set is `compatible` only when both the normal candidate-set compatibility
checks and the compatibility policy accept it.

Policy rejection reasons are bounded to:

- `candidate_limit_exceeded`;
- `runtime_capability_required`;
- `module_blocked_by_policy`;
- `publisher_not_allowed`.

Changing the policy creates a new `mcp-*` identity and therefore a different
policy-bound decision, even when the runtime snapshot and candidate artifacts
are unchanged. Consumers must bind decisions to the currently selected policy
identity rather than treating an older policy decision as interchangeable.

## Safety boundary

Both new contracts are evidence only and carry explicit invariants:

- `installation_authorized = false`;
- `execution_authorized = false`;
- `production_mutation_enabled = false`;
- `external_publication_authorized = false`.

A `compatible` result is not installation approval and does not grant execution
authority.

## Contract qualification scope

Targeted contract coverage includes:

- deterministic policy identity independent of input ordering;
- canonical publisher restriction semantics;
- compatible pass-through for a permissive policy;
- explicit module blocking;
- publisher allow-list rejection;
- policy-required runtime capability rejection;
- bounded candidate-count policy;
- preservation of base candidate-set incompatibility;
- fail-closed rejection of tampered policy identity;
- policy-version binding to decision identity;
- closed, non-authorizing JSON schemas.

No persistent-state migration is required by this contract.
