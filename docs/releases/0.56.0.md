# Home Center 0.56.0

Status: source package prepared for qualification.

## Область релиза

Home Center 0.56.0 добавляет явный выбор конкретного способа управления устройством поверх provider-resolution результата 0.54. Выбор является отдельной confirmation-gated операцией и не запускает enrollment, не получает credentials и не применяет политики.

Цепочка пользовательского действия теперь разделена на независимые безопасные этапы:

1. подтверждённое намерение перейти к подключению управления;
2. поиск доступных доверенных провайдеров;
3. явный выбор конкретного провайдера;
4. отдельное подтверждение выбора.

Выполнение выбранного провайдера в 0.56 отсутствует.

## Exact-state revalidation

Перед созданием provider-selection proposal Home Center повторно строит provider-resolution из текущего Household snapshot, подтверждённого enrollment proposal и текущего доверенного provider catalog.

Запрос обязан ссылаться на точный `resolution_plan_id` из предыдущего шага. Если изменились Household/device state, actor binding, provider catalog, readiness, поддерживаемая платформа или набор кандидатов, identity resolution меняется и старый выбор отклоняется fail-closed.

Пользовательская платформа по-прежнему считается неподтверждённой подсказкой:

- `platform_claim_source=user`;
- `platform_verified=false`.

Провайдер может быть предложен для выбора только если он присутствует среди текущих `ready=true` кандидатов и поддерживает заявленную платформу.

## Provider-selection proposal

Контракт: `home-center.device-management-provider-selection-proposal.v1`.

Proposal содержит детерминированный `proposal_id`, exact resolution/enrollment/catalog/Household identities и `proposed_provider_id`.

До подтверждения фиксируются:

- `confirmation_required=true`;
- `provider_selected=false`;
- `provider_ready=true`;
- `platform_supported=true`;
- `provider_execution_authorized=false`;
- `credential_access_authorized=false`;
- `enrollment_authorized=false`;
- `policy_application_authorized=false`;
- `managed_state_change_authorized=false`;
- `infrastructure_mutation_authorized=false`;
- `external_publication_authorized=false`.

`proposal_id` content-derived: изменение любого exact-state или provider-selection поля меняет identity и не может быть принято как исходное предложение.

## Единственный канонический выбор

Для одного подтверждённого enrollment в 0.56 допускается ровно один канонический подтверждённый provider selection. После успешного confirm Home Center сохраняет отдельную enrollment-scoped binding-запись, связывающую исходный enrollment proposal с exact selection proposal и confirmation receipt.

Если после этого попытаться подготовить другой provider selection для того же enrollment, операция отклоняется как конфликт. Неявная замена провайдера, silent overwrite и last-write-wins запрещены. Изменение ранее выбранного провайдера не входит в 0.56 и потребует отдельного явно подтверждаемого безопасного процесса.

Binding не является Desired State устройства и не предоставляет execution authority. Он нужен только для однозначности исторического выбора, идемпотентности и восстановления после прерванной записи результата.

## Confirmation receipt и восстановление

Контракт: `home-center.device-management-provider-selection-confirmation.v1`.

После явного подтверждения receipt фиксирует только факт выбора:

- `provider_selected=true`;
- точный `selected_provider_id`;
- исходные resolution/enrollment/catalog/Household identities;
- audit event identity.

Даже после подтверждения все execution/credential/enrollment/policy/managed-state/infrastructure/publication полномочия остаются `false`.

Повтор того же confirm идемпотентен и возвращает `already-confirmed` после проверки целостности сохранённого receipt. Позднейший drift readiness или catalog не переписывает исторический факт подтверждения, но любое будущее выполнение провайдера обязано выполнять собственную свежую revalidation.

Порядок durable-записи выбран так, чтобы canonical binding переживал прерывание между фиксацией подтверждённого выбора и завершением selection envelope. Если binding уже записан корректно, а envelope остался в pending-состоянии или не содержит receipt, повтор того же confirm восстанавливает envelope из проверенного binding без повторного выбора, нового audit-события или выдачи дополнительных полномочий. Повреждённый binding/receipt не восстанавливается «по догадке», а отклоняется fail-closed.

## API

Добавляются два аутентифицированных same-origin endpoint:

- `POST /api/v1/household/devices/enrollment/provider-selection/plan`;
- `POST /api/v1/household/devices/enrollment/provider-selection/confirm`.

Plan request принимает только exact resolution/enrollment identity, platform и provider id. Неизвестные поля отклоняются. Credentials, tokens, secrets, policy payload и execution flags API не принимает.

Confirm request принимает только selection `proposal_id` и явное `confirmed=true`.

После наличия canonical binding новый selection plan для того же enrollment возвращает конфликт; endpoint изменения уже подтверждённого выбора в 0.56 отсутствует.

## Интерфейс «Уютный»

После provider-resolution пользователь видит кнопку «Выбрать» у каждого текущего кандидата. Даже единственный кандидат не выбирается автоматически.

После нажатия Home Center сначала формирует selection proposal. Интерфейс проверяет exact provider/resolution identity и все safety flags, затем показывает отдельное подтверждение. Только после второго действия сохраняется факт выбора.

Пользователь получает явное сообщение, что:

- credentials не передаются;
- подключение не запускается;
- политики не применяются;
- Household device не становится managed;
- выбранный провайдер пока не получает execution authority.

После подтверждения текущий интерфейс блокирует повторный выбор в рамках этого действия. Серверная canonical binding дополнительно запрещает конкурентный или повторный выбор другого провайдера для того же enrollment независимо от состояния UI.

## Контракты

Добавлены закрытые JSON Schema:

- `contracts/devices/device-management-provider-selection-proposal.v1.schema.json`;
- `contracts/devices/device-management-provider-selection-confirmation.v1.schema.json`.

Оба контракта запрещают неизвестные поля и не содержат поля для credentials или секретов.

Canonical binding является внутренним durable envelope поверх тех же exact proposal/receipt contracts. Он не расширяет публичный API и не добавляет authority fields.

## Qualification boundary

Qualification 0.56 должна подтвердить:

- exact match с `resolution_plan_id` 0.54;
- повторную проверку confirmed enrollment и Household snapshot;
- повторную проверку provider catalog, readiness и platform compatibility;
- отклонение stale resolution/Household/catalog evidence;
- невозможность выбора провайдера вне текущего candidate set;
- невозможность передать credentials или execution flags через request;
- обязательный отдельный plan/confirm;
- content-derived selection proposal identity;
- ровно один canonical confirmed provider selection на enrollment;
- конфликт при попытке подтвердить другой provider selection для уже связанного enrollment;
- idempotent повтор того же confirmation без нового выбора и без выдачи authority;
- восстановление selection envelope из валидного canonical binding после прерванного завершения записи;
- fail-closed отказ при повреждённом binding или receipt;
- `provider_selected=true` только после confirm;
- сохранение всех execution/credential/enrollment/policy/managed-state/infrastructure/publication flags в `false`;
- отсутствие изменений Household managed state;
- наличие selection runtime в release wheel;
- соответствие «Уютного» интерфейса тем же fail-closed границам.

Persistent migration Household-state не требуется. 0.56 сохраняет отдельное provider-selection evidence и enrollment-scoped canonical binding в существующем StateStore; эти записи не являются Desired State устройства и не разрешают исполнение.
