# Home Center 0.57 — single-node technical Stable profile

Status: release-gate design for qualification; this document does not itself publish 0.57.0.

## Purpose

The canonical roadmap defines single-node Home Center as a complete supported mode and requires each started release train to reach PUBLIC STABLE. Multi-node/HA, concrete provider execution and commercial-launch clearance are separate claims: when their evidence is absent, they remain fail-closed, disabled or explicitly unclaimed rather than being reported as qualified.

For 0.57.0 the bounded technical Stable profile is therefore named `single-node-core`.

## Mandatory evidence

A `single-node-core` Stable decision is allowed only for one exact immutable version/revision and candidate artifact. The following remain hard gates:

- exact-head CI and exact source identity;
- reproducible artifact qualification;
- CodeQL/security, public privacy and infrastructure-neutrality checks;
- supported upgrade, rollback and user-state preservation;
- real target-node upgrade, readiness, user-state preservation and rollback evidence, content-addressed to the exact candidate artifact;
- source/deployment artifact SHA-256 identities;
- checksum sidecar and `SHA256SUMS`;
- qualification/acceptance/release manifests, public provenance and SPDX SBOM.

A missing or mismatched target-node artifact/environment/transcript digest fails closed.

## Target-node evidence semantics

Content addressing alone is not sufficient release evidence. The target environment and execution transcript must also be closed machine-readable documents rather than arbitrary opaque files.

The environment snapshot uses `home-center.target-node-environment.v1` and must bind:

- the exact target node identity and short hostname;
- Linux amd64/x86_64 architecture;
- bounded OS identity/version;
- `systemd` as the exercised service manager;
- the exact currently installed source release version/revision from which the real upgrade starts.

The execution transcript uses `home-center.target-node-execution-transcript.v1` and must bind:

- the exact 0.57 candidate version/revision and candidate artifact SHA-256;
- the same target node as the environment snapshot;
- `upgrade` as the exercised real-target operation;
- source identity equal to the environment snapshot;
- target identity equal to the candidate release;
- a content-addressed deployment transaction record;
- successful service activation plus `/readyz` HTTP 200 for the candidate when `health_ready=true`;
- the explicit user-state preservation observation used by the target-node decision;
- rollback to exactly the source version/revision;
- successful service activation plus `/readyz` HTTP 200 after rollback when rollback is claimed.

The local evaluator rejects unknown fields, duplicate JSON keys, unstructured text transcripts, cross-node evidence, cross-candidate evidence, source/rollback identity drift and health/rollback claims not backed by the corresponding structured observations. These checks do not fabricate real acceptance: the actual target execution still has to occur against the immutable candidate artifact.

## Explicitly unclaimed in this profile

A positive `single-node-core` decision sets all of the following to false:

- `ha_supported`;
- `provider_execution_supported`;
- `commercial_launch_cleared`;
- `release_authorized`;
- `external_publication_authorized`.

This means a technical Stable decision cannot be reused as evidence for HA, concrete provider execution, commercial launch or publication authority.

The existing full promotion gate remains available for a release/profile that intentionally claims multi-node HA, a concrete qualified provider adapter and commercial/legal clearance. No evidence is converted, inferred or fabricated between the two profiles.

## Provider execution boundary

0.57 contains the typed enrollment execution boundary, but the `single-node-core` Stable profile does not claim production provider execution. Without a deliberately registered qualified adapter, execution remains fail-closed. Provider command acceptance is never equivalent to successful enrollment or `managed=true`.

## Next release step

After this profile/gate and the semantic evidence tooling pass exact-head qualification in the runner-enabled release flow, the remaining release-specific technical work is to execute the real target-node upgrade/readiness/state-preservation/rollback procedure against the immutable 0.57 candidate artifact and feed those exact structured evidence files into the target-node evaluator. Only then can a separate explicit publication/promotion action be considered.
