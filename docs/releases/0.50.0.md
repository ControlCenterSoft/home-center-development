# Home Center 0.50.0

Status: runner-free development slice.

Home Center 0.50 starts the protected Desired State boundary for Household policy. This slice converts one already resolved `EffectivePolicy` into a deterministic next-generation Desired State plan without granting authority to apply it and without contacting any infrastructure provider.

## Protected Household Desired State

The new `household_desired_state_0500` boundary:

- accepts one exact `EffectivePolicy`;
- binds the exact household, member, role and policy identity;
- projects only the closed Household policy fields already present in the product model;
- requires an explicit current Desired State generation;
- emits exactly the next generation and rejects generation overflow;
- derives a deterministic plan identity from the complete policy and generation evidence;
- rejects stale-generation replay, policy substitution and altered plan contents during validation;
- keeps external publication disabled.

The plan contract is closed and versioned as `home-center.household-desired-state-plan.v1`.

## Safety boundary

This 0.50 slice is planning-only. It does **not**:

- write Desired State to persistent runtime storage;
- create operating-system, Samba AD or directory accounts;
- change DNS, internet filtering, VPN, MDM, files or smart-home providers;
- enroll or mutate a physical device;
- call a provider, shell, SSH or network transport;
- activate NAT, port-forwarding or external publication;
- create execution Jobs or grant production mutation authority.

Every plan carries `approval_required=true`, while `mutation_authorized`, `provider_execution_enabled` and `production_mutation_enabled` remain `false`.

## Fail-closed behavior

Planning rejects:

- invalid or exhausted generations;
- non-boolean policy values;
- invalid role or internet-policy enum values;
- effective policy evidence that attempts to enable external publication;
- stale generation during plan validation;
- substitution of another member's policy;
- any direct plan whose next generation is not exactly `expected_generation + 1`.

## Release-line integration

This work is intentionally isolated from provider execution and from the 0.49 member-confirmation implementation. Before 0.50 promotion it must be rebased/reconciled onto the exact qualified 0.49 line, after which release identity, packaging membership, API/runtime persistence integration and all required qualification gates must be completed on the resulting exact head.

## Next bounded stages

Later 0.50 work may add protected persistence and explicit confirmation of the Desired State projection, followed only then by narrowly scoped provider-backed provisioning. Each provider transition must retain optimistic state checks, audit evidence, recovery/rollback semantics and independent authority gates.

No future stage may infer permission to mutate infrastructure merely from possession of this planning object.
