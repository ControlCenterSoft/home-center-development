# Home Center 0.62.0

Status: source development in progress; not Release Candidate and not Public Stable.

## Scope prepared so far

0.62 continues the Roadmap role-driven identity/account provisioning line on top of the Policy Composer and parental-policy foundations already present in the current Stable lineage. Canonical Public Stable at preparation time is 0.61.0.

Prepared source boundaries now include:

- typed local/directory identity-provider capability evidence;
- exact Household snapshot/member/role/policy/provider binding;
- deterministic content-addressed provisioning plan;
- explicit local vs portable home-directory and profile modes;
- strict reconstruction that rejects unknown fields, evidence tampering and authority escalation;
- Cozy and Full plan projections that do not claim an account was created;
- explicit isolation of the existing local emergency administrator;
- explicit confirmation of the exact current plan;
- content-addressed read-only account-absence/name-conflict preflight evidence;
- bounded preflight freshness with future/stale evidence rejection;
- deterministic `confirmed-awaiting-execution` receipt;
- typed create-account provider request with bounded `secret://` references only;
- provider result contract where command acceptance remains explicitly unverified;
- separate content-addressed read-back observation for account/home/profile state;
- bounded read-back freshness and exact provider-operation binding;
- post-condition verification that reports success only after account `present`, home directory `ready` and profile `ready` are all observed.

## Confirmation and provider request

Confirmation does not trust stale or caller-constructed plan evidence. The complete plan is strictly reconstructed and rebuilt against the current Household snapshot, member role, Effective/Composed Policy and exact provider capability evidence. Any drift fails closed.

The account preflight is read-only and accepts only a fresh exact-bound `absent` result. `exists` is an explicit conflict, while `unknown` is never treated as absence. The maximum freshness budget is five minutes and callers may require a stricter positive bound.

Neither a positive preflight nor confirmation creates an account. Only the later typed adapter-request boundary may authorize the exact create-account operation. That request never exposes credential values: it carries only bounded secret references and refuses them when the exact provider capability has not declared secret-reference support.

## False-success protection

Provider command acceptance is not success. The provider result remains `accepted` with `account_creation_verified=false`, `home_directory_verified=false`, `profile_verified=false` and `post_condition_verified=false`.

A separate fresh read-only observation is required and is bound to the exact provider operation, provider identity/evidence and account name. `absent`, `missing` and `unknown` states all fail closed. Only an exact fresh observation of account `present`, home directory `ready` and profile `ready` can produce verified post-condition evidence.

## Safety boundary

The prepared source line does **not** yet register or invoke a concrete production identity provider, expose a public account-mutation endpoint or persist a successful identity transition into a durable runtime workflow.

It also never authorizes:

- raw password/token/credential value transfer;
- emergency local administrator mutation;
- arbitrary operating-system, sudo/root, directory-admin or equivalent privilege grants;
- generic infrastructure mutation;
- external publication.

Reserved emergency account names `admin`, `administrator` and `root` remain rejected. Portable home/profile requests fail closed unless the exact provider evidence advertises support.

## Remaining work before supported provisioning

Before 0.62 can become an actual supported provisioning release, remaining work includes:

- durable Job/Audit/idempotency around provider invocation and verification;
- exact account-conflict revalidation immediately before the durable mutation boundary;
- timeout/transport ambiguity handling without unsafe automatic retry;
- restart recovery without duplicate provider invocation;
- recovery/cleanup semantics for partial outcomes;
- supported concrete local/directory adapters and exact qualification evidence;
- authenticated API/UI wiring through existing authorization, re-auth and same-origin protections;
- final install/upgrade, packaging, security and release qualification for the exact 0.62 identity.

Current Public Stable remains 0.61.0. This source preparation does not change `VERSION`, create a release candidate, claim provider/HA support or grant commercial-launch clearance.
