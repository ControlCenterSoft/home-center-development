# Home Center 0.62.0

Status: source foundation prepared; not Release Candidate and not Public Stable.

## Scope prepared in this slice

0.62 continues the Roadmap role-driven identity/account provisioning line on top of the Policy Composer and parental-policy foundations already present in the current Stable lineage. Canonical Public Stable at preparation time is 0.61.2.

Prepared source boundaries:

- typed local/directory identity-provider capability evidence;
- exact Household snapshot/member/role/policy/provider binding;
- deterministic content-addressed provisioning plan;
- explicit local vs portable home-directory and profile modes;
- strict reconstruction that rejects unknown fields, evidence tampering and authority escalation;
- Cozy and Full plan projections that do not claim an account was created;
- explicit isolation of the existing local emergency administrator;
- confirmation-gated typed provider execution request using only `secret://` references;
- exact-bound read-only account-absence/name-conflict preflight with freshness and fail-closed `exists` / `conflict` / `unknown` handling;
- durable Job persisted before provider mutation and append-only Audit evidence for the execution outcome;
- deliberately registered typed runtime adapter requiring separate `start` mutation and read-only `observe` methods;
- provider start is invoked at most once for one durable idempotent attempt; timeout/malformed/ambiguous provider outcome becomes a failed non-retry-safe Job and is never automatically replayed;
- exact provider-operation-bound read-back observation and post-condition verification for account identity, home directory and profile;
- provider command acceptance remains non-success until fresh read-back proves the exact requested post-condition;
- replay of a succeeded idempotency key returns persisted verified evidence without provider reinvocation; replay of a failed attempt cannot silently retry the provider;
- secret reference values are not persisted in Job/Audit evidence; only count and content digest are retained;
- separate fail-closed member/account binding transition consumes only the persisted verified execution receipt, revalidates current parent/admin authority and the exact Household snapshot, persists one content-addressed binding with CAS/read-back, and never reinvokes the provider;
- the binding transition keeps credential material absent, the emergency local administrator isolated, privilege grants unauthorized and external publication unauthorized;
- conflicting or stale Household/binding state fails closed and cannot overwrite an existing binding; replay of the exact successful transition returns the same durable receipt without duplicate Job/Audit state;
- backup/restore qualification preserves the durable verified execution Job, binding state, transition receipt and Audit chain;
- fail-closed real-provider qualification evidence binds the exact Home Center candidate, provider artifact/version/kind/roles, real target, create/read-back transcripts and advertised capability set;
- a qualification decision can materialize server-side `IdentityProviderCapability` only after all mandatory evidence passes; incomplete evidence produces no trusted capability and grants no execution/infrastructure/publication authority;
- portable home/profile capability claims require their own real-provider exercise instead of inheriting a generic account-create PASS;
- source-prepared production API boundary uses authenticated same-origin plan/preflight/execute endpoints; provider capability and preflight observations are server-resolved and cannot be supplied by the HTTP client;
- execution through the API requires explicit confirmation and an idempotency key, revalidates current Household parent/admin authority, rebuilds the exact plan, obtains a fresh adapter preflight and only then enters the durable execution runtime;
- without a registered exact-qualified provider the API remains fail-closed/unavailable rather than falling back to an unqualified adapter;
- wheel and node deployment artifact membership qualification covers the 0.62 planning, preflight, execution, verification, binding-transition, provider-qualification and API runtimes plus their closed JSON schemas.

## Safety boundary

This source slice does **not**:

- provide a built-in production local or directory provider adapter;
- create or modify a directory object except through a separately registered qualified adapter;
- accept provider capability/qualification evidence or provider preflight observations from an HTTP client;
- set, return or persist password/token/credential values;
- grant operating-system, sudo/root, directory-admin or similar privileges;
- change the emergency local administrator identity;
- automatically retry an ambiguous provider mutation;
- claim provider command acceptance as account-creation success;
- let the external provider receipt mutate Home Center member/account state directly; the local binding is a separate exact-state transition after verified read-back;
- publish any service externally.

Reserved emergency account names `admin`, `administrator` and `root` are rejected by the planning contract. Portable home/profile requests fail closed unless exact provider evidence explicitly advertises support. Execution revalidates a still-fresh exact account-absence observation immediately before the durable Job and provider call. Credentials remain opaque `secret://` references; credential-value access stays unauthorized. Read-back observations are read-only, exact-bound and secret-free. The separate binding transition revalidates current Household state and parent/admin authority, persists no credential material, and has no provider-call path. Provider qualification evidence is descriptive/admission evidence only and never replaces the runtime confirmation, preflight, execution, read-back or binding-transition boundaries.

## Required before executable provisioning is complete

Before 0.62 can claim a production identity provisioning capability, at least one concrete local and/or directory adapter must be implemented and exercised through the exact-bound qualification contract on a real target/provider. The evidence must match the exact 0.62 candidate and the exact advertised capability set; evidence from another candidate or from an unexercised portable-home/profile mode is not transferable.

The source-prepared API/runtime wiring must receive runner qualification together with the current verified binding transition and exact-qualified provider registration path. Then 0.62 still requires exact release identity, supported install/upgrade/rollback qualification from Public Stable 0.61.2, final security/release artifact gates and guarded Public Stable promotion. Multi-node HA and commercial-launch claims remain separate qualification/activation boundaries.

Current Public Stable is 0.61.2. This preparation does not change `VERSION`, create a release candidate, claim provider/HA support or grant commercial-launch clearance.
