# Home Center 0.64.0

Status: source preparation only; not Release Candidate and not Public Stable.

Authoritative Public Stable baseline for this work is Home Center 0.63.0.

## Scope

0.64 introduces the bounded foundation for Recommendations and safe auto-repair. Eligibility remains intentionally non-executing: it evaluates whether an exact repair candidate is eligible for a future automatic repair path under an explicit policy allowlist.

Eligibility requires all of the following:

- a typed action from the closed Home Center repair-action set;
- exact Household/resource generation binding;
- content-addressed evidence;
- an explicit policy identity and digest;
- a policy-allowed risk class;
- proven recovery semantics;
- a verifiable post-condition;
- no required provider execution;
- no generic infrastructure mutation;
- no external publication.

The recommendation identity is deterministic and changes when the source generation, evidence or policy changes. Unknown or disallowed conditions fail closed.

The development line includes a bounded durable recommendation-history adapter. It stores the exact recommendation projection and timestamp in an append-only-by-identity form, supports bounded Household/resource history reads and treats exact replay idempotently. The adapter deliberately does not self-migrate; canonical StateStore schema installation remains a separate gate.

A separate admission-revalidation contract compares the previously reviewed recommendation with a freshly rebuilt recommendation from current resource evidence and current policy. Generation drift, evidence drift, policy drift or any new blocker prevents Job admission. A positive admission is still evidence only.

The current source line also defines the transport-neutral typed repair Job lifecycle. Job identity is deterministically bound to the exact admission/recommendation and a SHA-256-only idempotency key. The lifecycle is `admitted → running → verifying → succeeded/failed`; an ambiguous execution result becomes `reconcile-required` and never receives automatic retry. An accepted effect receipt is not success: only separate verified post-condition evidence can produce `succeeded`.

## Safety boundary

`eligible_for_auto_repair=true` and `admissible_for_job=true` are bounded evidence states. Neither grants execution authority. The Job lifecycle itself also does not call an adapter; it only defines safe state transitions and false-success prevention.

Recommendation, history, admission and Job contracts keep generic execution, provider execution, infrastructure mutation and external publication unauthorized. The raw idempotency key is never part of durable Job projection.

Durable recommendation history stores no command, provider payload, credential or repair output. A blocked recommendation is retained as blocked evidence rather than converted into a success path.

The future execution layer must repeat authoritative state checks at the mutation boundary, use an action-specific adapter, persist Audit/recovery evidence and verify the authoritative post-condition before user-visible success. An interrupted or ambiguous repair must never be re-invoked automatically or reported as successful without verified read-back.

## Commercial and security boundary

This foundation adds no third-party runtime dependency and no remote-service client dependency. It does not claim provider qualification, HA capability or commercial-launch/legal clearance. Those remain separate release/profile boundaries.

## Next required work

Before 0.64 can become a release candidate, subsequent slices must install recommendation/history and Job state through the canonical StateStore migration/persistence path, connect Job admission to authenticated/RBAC-gated product runtime, add bounded action adapters, authoritative read-back/post-condition verification, restart/recovery behavior, UI history/explanation and the normal exact release identity/install/upgrade/security/packaging qualification.
