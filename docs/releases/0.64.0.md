# Home Center 0.64.0

Status: source preparation only; not Release Candidate and not Public Stable.

Authoritative Public Stable baseline for this work is Home Center 0.63.0.

## Scope

0.64 introduces the bounded foundation for Recommendations and safe auto-repair. Eligibility remains intentionally non-executing: it evaluates whether an exact repair candidate is eligible for a future automatic repair path under an explicit policy allowlist.

Eligibility requires all of the following:

- a typed action from the closed Home Center repair-action set;
- exact Household/resource generation binding;
- content-addressed evidence;
- an explicit policy identity and digest;
- a policy-allowed risk class;
- proven recovery semantics;
- a verifiable post-condition;
- no required provider execution;
- no generic infrastructure mutation;
- no external publication.

The recommendation identity is deterministic and changes when the source generation, evidence or policy changes. Unknown or disallowed conditions fail closed.

This development slice also adds a bounded durable recommendation-history adapter. It stores the exact recommendation projection and timestamp in an append-only-by-identity form, supports bounded Household/resource history reads and treats exact replay idempotently. The adapter deliberately does not self-migrate; canonical StateStore schema installation remains a separate gate.

## Safety boundary

`eligible_for_auto_repair=true` is evidence only. It does not grant execution authority and does not start a Job. The recommendation contract and durable history keep execution, provider execution, infrastructure mutation and external publication unauthorized.

Durable recommendation history stores no command, provider payload, credential or repair output. A blocked recommendation is retained as blocked evidence rather than converted into a success path.

Any later automatic repair execution path must separately bind the exact recommendation to a durable typed Job, revalidate current state immediately before mutation, use an action-specific adapter, persist Audit/recovery evidence and verify the authoritative post-condition before user-visible success. An interrupted or ambiguous repair must never be reported as successful without verified read-back.

## Commercial and security boundary

This foundation adds no third-party runtime dependency and no remote-service client dependency. It does not claim provider qualification, HA capability or commercial-launch/legal clearance. Those remain separate release/profile boundaries.

## Next required work

Before 0.64 can become a release candidate, subsequent slices must install recommendation history through the canonical StateStore migration path, add explicit repair admission policy, typed repair Job lifecycle, bounded action adapters, authoritative read-back/post-condition verification, restart/recovery behavior, UI history/explanation and the normal exact release identity/install/upgrade/security/packaging qualification.
