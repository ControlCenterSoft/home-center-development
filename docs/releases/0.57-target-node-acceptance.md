# Home Center 0.57 — real target-node acceptance

Status: runner-free preparation for the remaining `single-node-core` Stable gate. This procedure does not itself publish or promote a release.

## Exact candidate boundary

The acceptance must exercise the immutable deployment candidate produced for the exact 0.57 release identity. For the currently qualified candidate:

- version: `0.57.0`;
- revision: `ccdbfb37c5e441d3e18f2ef34c77fee70f44c2a5`;
- deployment archive SHA-256: `85f848e519d72aebe0767c0b8ece71516c1a2ae145ff8f1c9b89ead5a4bf5eac`.

The archive must not be rebuilt for target acceptance. Any different archive digest or release revision is a different candidate and needs its own qualification chain.

## Acceptance helper

`scripts/capture_target_node_acceptance.py` is a target-local, stdlib-only helper. It does not contact GitHub and does not invoke Actions or any CI mechanism. It:

1. verifies the candidate archive digest, version/revision and the manifest-bound install/rollback scripts;
2. verifies the currently installed release identity and baseline HTTPS `/readyz`;
3. records only bounded/sanitized environment evidence — no IP/domain, configuration contents, credentials or secret values;
4. computes a digest of protected files (`config`, local-admin verifier file, session key and audit key) without exporting their contents;
5. computes a logical digest of durable SQLite state while excluding only runtime-maintained `audit`, `cluster_meta`, `nodes` and SQLite sequence data;
6. upgrades with the candidate's own `deploy/install-node.sh` and exact expected-current identity;
7. requires candidate service readiness and exact release identity;
8. requires both protected-file and durable-state digests to remain unchanged;
9. exercises the candidate's own `deploy/rollback-node.sh`;
10. requires the original release identity/readiness and protected/durable state to be restored exactly;
11. only after all checks pass emits `target-environment.json`, `target-transcript.json` and `target-node-evidence.json` as owner-only evidence files.

If acceptance fails after candidate installation, the helper attempts the exact rollback automatically. Failure of that emergency rollback is emitted separately as a critical condition and must never be converted into PASS evidence.

## Mutation-free preflight

Run the helper first with `--plan-only`. This validates the artifact, current installation, protected-state readability, systemd and current HTTPS readiness, then prints the planned steps without changing the node and without producing qualification evidence.

Example shape:

```text
sudo python3 scripts/capture_target_node_acceptance.py \
  --candidate-artifact /path/to/home-center-0.57.0-linux-amd64.tar.gz \
  --candidate-sha256 85f848e519d72aebe0767c0b8ece71516c1a2ae145ff8f1c9b89ead5a4bf5eac \
  --expected-candidate-version 0.57.0 \
  --expected-candidate-revision ccdbfb37c5e441d3e18f2ef34c77fee70f44c2a5 \
  --expected-current-version 0.56.0 \
  --plan-only
```

If the current Stable revision is known from the target installation record, also pass `--expected-current-revision`; a mismatch then fails before mutation. `--ready-host` may be supplied when the configured management bind address is not the TLS name/IP used for local verification. Its value is never written into evidence.

## Real acceptance run

After the mutation-free plan passes, rerun without `--plan-only` and provide a fresh empty evidence directory. The helper is designed to leave the target on its original release after the successful rollback exercise.

The emitted manifest is the closed `home-center.target-node-evidence.v1` input for `scripts/evaluate_target_node_evidence.py`. That evaluator must still recompute and bind the candidate archive, environment file and transcript SHA-256 values before producing the `home-center.target-node-qualification.v1` decision.

## Claim boundary

A PASS here proves only the exact candidate's single-target install/upgrade, readiness, protected/user-state preservation and rollback on the exercised environment. It does not prove or enable:

- multi-node/HA;
- a concrete provider adapter or provider execution;
- external publication;
- commercial launch clearance;
- Public Stable publication authority.

Those claims remain independently fail-closed. The target-node decision is one required input to the bounded `single-node-core` technical Stable profile.
