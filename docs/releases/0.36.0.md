# Home Center 0.36.0

Status: development qualification candidate.

Home Center 0.36 adds exact-state revalidation for module candidate-set
decisions that are already bound to a versioned compatibility policy. The
package does not install modules, execute module actions, mutate
infrastructure, or publish services externally.

## Policy-bound revalidation

`revalidate_module_candidate_set_under_policy()` treats the previous
`home-center.module-policy-candidate-set-decision.v1` as untrusted evidence.
Before using it, Home Center reconstructs the original decision from the exact
compatibility-policy snapshot, runtime compatibility snapshot, manifests, and
verified module artifacts.

The previous decision is rejected fail-closed when reconstruction does not
produce the exact same serialized contract.

After reconstruction, Home Center independently evaluates fresh evidence.
Callers may provide:

- a fresh runtime compatibility snapshot;
- a fresh compatibility-policy snapshot;
- a fresh candidate set.

When fresh policy or candidate inputs are omitted, their original exact inputs
remain selected. The fresh runtime snapshot is always explicit.

## Drift model

The returned
`home-center.module-policy-candidate-set-revalidation.v1` contract records the
original and fresh:

- policy identities and policy versions;
- candidate-set decision identities;
- runtime compatibility snapshot identities;
- aggregate and base compatibility states;
- base, policy-specific, and combined blocked-module sets;
- missing policy-required runtime capabilities;
- policy rejection reasons;
- per-module publisher and policy-reason outcomes.

The previous decision is `current` only when all bound evidence remains
identical after canonical reconstruction and fresh evaluation.

A result becomes `stale` when any relevant boundary changes, including:

- compatibility-policy identity or policy version;
- runtime compatibility snapshot;
- candidate-set identity or membership;
- base compatibility result;
- policy-blocked or combined blocked-module sets;
- required-runtime-capability outcome;
- aggregate policy result or per-module policy outcome.

A changed policy identity invalidates the old exact-state decision even when
the new policy produces the same compatibility status. A changed runtime
snapshot or candidate-set identity similarly invalidates the old decision even
when all candidates remain compatible.

Candidate ordering alone is not drift because candidate-set evaluation is
canonical.

## Tamper resistance

Revalidation never trusts caller-supplied decision IDs or serialized status
fields. The original decision must be reproduced by the existing policy-bound
candidate-set evaluator.

Tampered original evidence is rejected with
`original_policy_candidate_set_evidence_rejected`. Malformed or tampered fresh
policy/candidate evidence is rejected with
`fresh_policy_candidate_set_evidence_rejected`.

The revalidation identity uses deterministic canonical JSON hashing and is
stable for the same trusted inputs.

## Safety boundary

The revalidation contract is evidence only and always carries:

- `installation_authorized = false`;
- `execution_authorized = false`;
- `production_mutation_enabled = false`;
- `external_publication_authorized = false`.

Neither `current` nor a fresh `compatible` decision grants installation or
execution authority.

## Contract qualification scope

Targeted contract coverage includes:

- unchanged evidence remaining `current` with deterministic identity;
- policy-version drift;
- policy-rule drift that changes module outcomes;
- runtime-snapshot drift that remains compatibility-safe;
- candidate-artifact drift;
- canonical candidate ordering;
- rejection of tampered original decision evidence;
- rejection of tampered original policy evidence;
- rejection of tampered fresh policy evidence;
- closed and explicitly non-authorizing JSON schema.

No persistent-state migration is required by this contract.
