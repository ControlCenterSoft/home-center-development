# Home Center 0.33.0

Status: development qualification candidate.

Home Center 0.33 extends module admission with deterministic cross-candidate
compatibility evidence. The new boundary evaluates a bounded set of module
candidates against one exact runtime compatibility snapshot before any
installation or execution authority can exist.

## Module candidate-set compatibility

`evaluate_module_candidate_set()` accepts one canonical
`home-center.module-compatibility-snapshot.v1` and a bounded set of
Manifest v2 plus verified-artifact pairs.

The evaluator:

- reconstructs the supplied runtime snapshot and rejects tampered snapshot evidence;
- validates every candidate manifest through the existing product/module admission boundary;
- requires a unique module ID for every candidate in the set;
- overlays candidate versions on the installed-module map only for compatibility analysis;
- evaluates required and optional dependency version ranges against that planned module state;
- detects conflicts between candidates as well as conflicts with already installed modules;
- preserves exact manifest, artifact and provenance verification through the existing admission evaluator;
- normalizes candidate ordering so the same logical set has the same evidence identity.

This allows a dependency that is absent from the current installed state to be
satisfied by another candidate in the same planned set, while still failing
closed if the candidate version is outside the declared dependency interval.

## Evidence contract

The result uses the closed
`home-center.module-candidate-set-decision.v1` contract and contains:

- canonical runtime snapshot identity;
- current installed-module state;
- candidate-overlaid planned module state;
- one exact `module-admission-decision.v1` reference per candidate;
- compatibility status and reasons for each candidate;
- the normalized list of blocked module IDs;
- deterministic `mcsd-*` identity.

The set is `compatible` only when every candidate is compatible in the combined
planned state. Otherwise the set is `blocked`.

## Safety boundary

Candidate-set evaluation is read-only compatibility evidence. It does not
install or upgrade modules, execute lifecycle actions, create Jobs or Changes,
alter Desired State or Actual State, change network/storage/cluster
configuration, authorize production mutation or authorize external publication.

The evidence explicitly keeps `installation_authorized`,
`execution_authorized`, `production_mutation_enabled` and
`external_publication_authorized` set to `false`.

## Qualification boundary

Targeted contract tests cover dependency satisfaction inside one candidate set,
cross-candidate conflicts, dependency-version mismatch, candidate replacement
of an installed version for analysis, deterministic ordering, duplicate
candidate rejection, snapshot tamper rejection and the closed non-authorizing
JSON schema.

The 0.33 branch remains a development candidate until the separate qualification
and release gates pass.
