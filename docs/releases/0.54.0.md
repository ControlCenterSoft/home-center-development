# Home Center 0.54.0

Status: source package ready for qualification.

## Scope

Home Center 0.54.0 adds the next bounded «Уютный → Семья» step after confirmed enrollment intent: discovery of real device-management provider capabilities and a provider-resolution plan.

The release introduces a trusted local provider catalog. The catalog is empty by default. Home Center does not ship fake, placeholder or implicitly available MDM providers. A provider is a candidate only when it is present in the trusted local registry, reports `ready=true` and explicitly supports the platform supplied for the device.

## Provider catalog

The provider catalog is closed and deterministic. Each profile contains:

- stable `provider_id` and display name;
- explicitly supported platforms;
- supported enrollment modes;
- readiness state.

The public Household API in this release is read/planning-only with respect to this catalog: there is no Cozy/API endpoint that lets a user invent or register a provider, inject credentials or mark a provider ready.

Missing catalog state is treated as a valid empty catalog. Malformed stored catalog state is rejected fail-closed instead of being treated as available provider evidence.

## Provider resolution

Resolution requires a confirmed 0.53 enrollment proposal and revalidates that proposal against the exact current Household snapshot before returning candidates.

The user supplies the device platform as a hint. Home Center records this as:

- `platform_claim_source=user`;
- `platform_verified=false`.

The platform claim is therefore not represented as automatically discovered device truth.

The resolution state is:

- `unavailable` — no ready trusted provider supports the claimed platform;
- `single-candidate` — exactly one ready trusted provider matches;
- `choice-required` — multiple ready trusted providers match.

Even when there is exactly one candidate, Home Center does not select it automatically. Every resolution plan fixes `provider_selection_required=true` and `selected_provider_id=null`.

## Safety boundary

Provider-resolution plans and every serialized provider candidate are non-authorizing. The plan fixes:

- `provider_execution_authorized=false`;
- `policy_application_authorized=false`;
- `managed_state_change_authorized=false`;
- `infrastructure_mutation_authorized=false`;
- `external_publication_authorized=false`.

Each candidate additionally exposes `execution_authorized=false`.

0.54 does not select a provider, create an enrollment token, read or write provider credentials, execute enrollment, install MDM profiles, apply DNS/VPN/Wi-Fi/firewall/filtering policy, change the Household device `managed` flag, mutate external Desired State or publish a service externally.

## API

Adds authenticated, same-origin:

`POST /api/v1/household/devices/enrollment/provider-resolution/plan`

Request schema: `home-center.device-management-provider-resolution-request.v1`.

The request contains only the confirmed enrollment proposal id and the user-supplied device platform. It does not accept a selected provider id or credentials.

No provider-selection or provider-execution endpoint is introduced in this release.

## Cozy interface

After successful 0.53 enrollment confirmation, «Уютный» offers «Найти способ управления». The user explicitly selects the device type and starts resolution.

The interface fail-closed validates that:

- the platform remains unverified user input;
- provider selection is still required;
- `selected_provider_id` is null;
- all execution, policy, managed-state, infrastructure and publication authority flags remain false;
- every candidate is non-authorizing.

For an empty catalog it says that no management method is currently available and that nothing will be installed. One candidate is shown as found but not selected. Multiple candidates are displayed as choices for a future separate selection step.

## Qualification boundary

0.54 qualification is cumulative over the 0.49–0.53 confirmed Household/member/device/management/enrollment boundaries. The release wheel must contain `device_management_provider.py` and `device_management_provider_runtime.py` in addition to all previous runtime boundaries.

No persistent Household-state migration is required.
