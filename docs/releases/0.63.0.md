## Scope

0.63 prepares bounded QR guest/device onboarding within the canonical roadmap after Public Stable 0.62.1.

Current qualified source boundaries include:

- parent-only immutable onboarding invitation;
- guest or exact-device subject binding;
- 60–1800 second TTL;
- single-use onboarding code with only SHA-256 persisted in durable invitation evidence;
- ephemeral QR payload explicitly classified as a short-lived onboarding code rather than an administrative credential;
- first-class expiration, revocation and consumed-state evaluation;
- deterministic redemption plan requiring a separate explicit confirmation;
- closed JSON contracts for invitation, QR payload, redemption plan, durable runtime record and operation receipt;
- exact Household `snapshot_id` / `resource_version` / `generation` binding in the durable runtime layer;
- exact target FamilyMember binding, including an enabled guest-only first runtime scope for guest onboarding;
- additive canonical StateStore migration for the QR runtime and operation tables without changing published migrations 1–3;
- transactionally guarded consume/revoke with exact record version and idempotency evidence;
- ephemeral code generation outside durable evidence;
- invitation-state read-back evidence after consume/revoke;
- strict issue/plan/consume/revoke request parsing with closed schemas, server-authoritative actor/time inputs and explicit confirmation;
- receipt-only StateStore Audit integration with correlation-ID validation and append-only hash-chain persistence;
- restart and backup/restore qualification proving consumed/revoked invitations cannot be resurrected and raw onboarding codes do not enter durable state;
- authenticated same-origin HTTP issue/plan/consume/revoke routes layered on the existing session, origin/CSRF, external-access and bounded-body fences;
- production server selection of the V10 HTTP handler so the qualified QR routes are reachable through the canonical server process while still using the production-safe Runtime composition.

## Safety boundary

QR presentation and invitation consumption do **not** create an account, register/bind a device, change `managed`, grant parent/admin privileges, execute a provider, mutate infrastructure or publish a service externally. Revoked, expired, consumed, stale-Household or code-mismatched invitations fail closed.

The QR payload must never contain a long-lived administrative credential, emergency-admin secret, directory administrator password or persistent API token. The short-lived onboarding code is single-use and must not be persisted or logged as durable evidence. Durable receipts explicitly report `onboarding_effect_verified=false`; their positive post-condition applies only to the invitation-state transition itself.

Guest runtime issuance is intentionally narrower than the foundation contract: the current first slice accepts only an existing enabled `guest` member and `internet.guest` scope. Device runtime issuance accepts only an already registered unmanaged device bound to the exact target member. This avoids inventing account/device creation authority in the QR layer.

The HTTP boundary does not accept client-supplied issuer/parent identity, server time, Audit correlation authority or effect evidence. It reuses the existing server authentication and same-origin/CSRF fences. Consuming an invitation still ends at the explicitly declared next boundary (`typed-guest-access-change-job` or `typed-device-binding-change-job`) and is not user-visible onboarding success.
