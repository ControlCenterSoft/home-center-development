## Safety boundary

QR presentation and invitation consumption do **not** create an account, register/bind a device, change `managed`, grant parent/admin privileges, execute a provider, mutate infrastructure or publish a service externally. Revoked, expired, consumed, stale-Household or code-mismatched invitations fail closed.

The QR payload must never contain a long-lived administrative credential, emergency-admin secret, directory administrator password or persistent API token. The short-lived onboarding code is single-use and must not be persisted or logged as durable evidence. Durable invitation receipts explicitly report `onboarding_effect_verified=false`; their positive post-condition applies only to the invitation-state transition itself.

Guest runtime issuance is intentionally narrow: only an existing enabled `guest` member and exact `internet.guest` scope are accepted. Device runtime issuance accepts only an already registered unmanaged device bound to the exact target member. The effect handoff and post-condition observation preserve this subject/scope shape and reject relabeling fail-closed.

A typed effect Job or provider/action acceptance is never user-visible success. Success requires a separate authoritative read-back bound to the exact handoff, Job and target. `unknown`, `not-satisfied`, stale, future-dated, cross-Job or digest-tampered read-back evidence cannot become a positive verification receipt.
