## Safety boundary

QR presentation and invitation consumption alone do **not** create an account, register/bind a device, change `managed`, grant parent/admin privileges, execute a provider, mutate infrastructure or publish a service externally. Revoked, expired, consumed, stale-Household or code-mismatched invitations fail closed.

The QR payload must never contain a long-lived administrative credential, emergency-admin secret, directory administrator password or persistent API token. The short-lived onboarding code is single-use and must not be persisted or logged as durable evidence. Durable QR invitation receipts report `onboarding_effect_verified=false`; their positive post-condition applies only to the invitation-state transition itself.

Guest runtime issuance remains deliberately bounded to an existing enabled `guest` member and the supported guest-access scope. Device runtime issuance accepts only an already registered unmanaged device bound to the exact target member. The effect path cannot broaden either boundary.

Effect execution is typed and server-authoritative. Provider execution, generic shell/command authority, infrastructure mutation and external publication remain closed unless a future separately qualified capability explicitly requires them. Provider or command acceptance is never treated as onboarding success. Unknown, stale or ambiguous actual state remains fail-closed and cannot become user-visible success.

Concrete provider/HA/commercial-launch claims remain separate qualification boundaries. Technical Public Stable qualification must remain distinct from any unqualified commercial-launch claim. The bounded `single-node-core` profile therefore keeps multi-node HA/automatic failover, universal concrete provider execution and commercial launch clearance unclaimed unless separately qualified.
