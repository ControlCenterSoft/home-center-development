## Safety boundary

QR presentation and invitation consumption do **not** create an account, register/bind a device, change `managed`, grant parent/admin privileges, execute a provider, mutate infrastructure or publish a service externally. Revoked, expired, consumed, stale-Household or code-mismatched invitations fail closed.

The QR payload must never contain a long-lived administrative credential, emergency-admin secret, directory administrator password or persistent API token. The short-lived onboarding code is single-use and must not be persisted or logged as durable evidence. Durable QR receipts explicitly report `onboarding_effect_verified=false`; their positive post-condition applies only to the invitation-state transition itself.

Guest runtime issuance is intentionally narrower than the foundation contract: the current runtime accepts only an existing enabled `guest` member and `internet.guest` scope. Device runtime issuance accepts only an already registered unmanaged device bound to the exact target member. Effect handoff/admission cannot broaden either boundary.

Effect handoff and durable Job admission remain deliberately non-executing. An admitted Job stays in `preflight` with pending typed-effect execution, authoritative read-back and post-condition verification. `execution_authorized=false`, `post_condition_verified=false` and `effect_success_claimed=false` at this boundary. User-visible onboarding success is forbidden until a later exact effect execution path has been followed by authoritative product-state read-back and positive verification.
