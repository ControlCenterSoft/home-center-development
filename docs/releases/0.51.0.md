# Home Center 0.51.0

Status: official release.

## Scope

Home Center 0.51.0 extends «Уютный → Семья» with confirmation-gated registration of a device for one exact family member.

The new boundary deliberately separates **knowing about a device** from **managing a device**. A successful 0.51 confirmation only records the device in Household product state. It does not claim that Android MDM, VPN, DNS filtering, certificates, Wi‑Fi, account/profile settings or any other provider policy has been applied.

## Household device registration

The user selects a family member, enters a friendly device name and follows the same bounded pattern used for people:

`plan device → review owner / management requirement → explicit confirm`

The proposal is bound to the exact Household `snapshot_id`, `resource_version` and generation. The acting member is derived on the server from the authenticated actor binding; the client cannot nominate another administrator identity.

At planning time Home Center validates:

- the acting member is an enabled `parent` with household administration permission;
- the selected family member exists and is enabled;
- the generated device identifier does not already exist;
- the resulting Household still satisfies domain limits and referential integrity;
- the target role's effective policy is resolvable.

## Management-required is not management-applied

`RolePreset` remains authoritative for whether a managed device is required. For a child, `management_required=true` is surfaced to the Cozy UI. This is a requirement/status fact only.

Every newly registered device is persisted as `managed=false`. The proposal and receipt also fix these authority fields to false:

- `managed_after_registration=false`;
- `policy_application_authorized=false`;
- `provider_execution_authorized=false`;
- `infrastructure_mutation_authorized=false`;
- `external_publication_authorized=false`.

A future provider/MDM boundary must separately prove successful enrollment and post-condition verification before Home Center may change a device to managed state.

## Confirmation, stale-state protection and audit

Planning never mutates Household state. Confirmation requires an explicit `confirmed=true` request and revalidates the stored server-side proposal against its exact base snapshot and the caller's current actor/member binding.

If Household state changes between plan and confirm, the proposal is rejected as stale. Repeating a successfully completed confirmation returns an `already-applied` result and does not create a duplicate device.

Accepted registration records pre-apply and completion audit evidence around the Household product-state transition.

## Cozy UI

The authenticated `Семья` screen now exposes `Добавить устройство` only for a configured household. The owner selector is populated from the current Household snapshot. Before confirmation the user sees whether that member's role requires managed-device policy and is explicitly told that registration does not apply MDM or other provider settings.

The existing `Уютный ↔ Полный` switch, first-login password rotation, family-member plan/confirm workflow and 0.50 module compatibility-state boundary remain cumulative.

## Safety boundary

0.51 introduces no OS/directory account creation, no MDM enrollment, no DNS/VPN/Wi‑Fi/firewall changes, no provider execution, no external Desired State mutation and no NAT/port-forwarding/external publication.

## Qualification boundary

The release wheel contains both `household_device_change.py` and `household_device_runtime.py` in addition to all previously required runtime. Qualification passes on Python 3.12 and 3.13 with the full pytest suite, reproducible artifact qualification, public-repository privacy and infrastructure-neutrality gates on the exact release SHA.
