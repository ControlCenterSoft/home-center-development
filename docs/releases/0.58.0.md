# Home Center 0.58.0

**Статус:** разработка; не Release Candidate и не Public Stable.

## Цель релиза

0.58.0 добавляет отдельную fail-closed проверку фактического результата подключения устройства после provider-backed enrollment из 0.57. Принятие команды провайдером само по себе по-прежнему не означает успешное подключение и не разрешает выставлять `managed=true`.

## Реализуемая граница

Первый source-slice 0.58 вводит типизированную post-condition verification:

- read-only запрос к provider adapter привязан к конкретным `execution_job_id`, `plan_id`, `provider_operation_id`, устройству и текущему Household snapshot;
- одноразовые enrollment token/QR и любые значения секретов не переходят в verification boundary;
- результат провайдера принимается только при точном совпадении operation/device binding;
- отдельно проверяются наличие management certificate, management profile, agent и активное состояние управления;
- неизвестные поля и утверждение о наличии secret material отклоняются fail-closed;
- частичный результат формирует отрицательное evidence и **не** разрешает `managed=true`;
- положительное evidence детерминированно и разрешает только переход локального product-state `ManagedDevice.managed: false -> true`;
- применение политик, изменение инфраструктуры и внешняя публикация этим evidence не разрешаются;
- managed-state replacement привязан к точному Household `snapshot_id`/`resource_version`/generation и отклоняется как stale после любого конкурирующего изменения.

## Failed-enrollment cleanup и safe retry planning

Второй NR2 source-slice добавляет fail-closed обработку отрицательного post-condition evidence:

- отрицательное evidence повторно проверяется на внутреннюю целостность: набор `failure_reasons` должен точно соответствовать наблюдаемым certificate/profile/agent/management признакам;
- если provider-side следов подключения нет, формируется `no-provider-cleanup` plan;
- если остаётся хотя бы один provider-side след, формируется `de-enroll-required` plan с обязательным отдельным подтверждением;
- cleanup plan сам по себе всегда оставляет `provider_mutation_authorized=false`, `retry_planning_allowed=false`, `retry_execution_authorized=false` и не разрешает `managed=true`;
- после cleanup требуется **новый** более свежий read-back того же exact provider/device/execution binding;
- только если свежий read-back подтверждает отсутствие certificate/profile/agent и неактивное управление, может появиться `retry_planning_allowed=true`;
- даже в этом случае `retry_execution_authorized=false`: фактический повтор обязан снова пройти штатные 0.57 plan/confirm/execution gates;
- mismatch exact binding, не более свежий read-back и tampered evidence блокируются fail-closed.

## Явный de-enrollment boundary

Третий NR2 source-slice подготавливает отдельно подтверждаемую provider mutation для случая `de-enroll-required`:

- de-enrollment plan строится только из exact cleanup evidence и того же текущего Household snapshot/resource_version/generation;
- план доступен только включённому Household actor с `administration_allowed=true` и не создаётся для child/guest;
- до подтверждения `provider_mutation_authorized=false`; plan отдельно требует durable Job и Audit;
- confirmation привязано к точному de-enrollment plan, actor, idempotency key и времени подтверждения;
- только после подтверждения формируется узкий adapter request для одного provider/device/operation; значения credentials и одноразовые enrollment artifacts через него не передаются;
- принятие de-enrollment команды провайдером формирует только `provider-cleanup-accepted`: `post_cleanup_verified=false`, `retry_planning_allowed=false`, `retry_execution_authorized=false`;
- неизвестные поля и попытка adapter result объявить cleanup уже проверенным или разрешить retry отклоняются fail-closed;
- после provider acceptance всё равно обязателен свежий read-back и отдельная retry assessment; новый enrollment никогда не стартует автоматически.

## Durable post-condition verification runtime и API

Четвёртый NR2 source-slice добавляет durable runtime для read-only verification, подключает его к composition root и вводит отдельный защищённый HTTP endpoint проверки:

- verification разрешается только для exact 0.57 execution receipt в состоянии `provider-accepted`, чей durable execution Job действительно завершился успешно и принадлежит тому же actor;
- отменённая, незавершённая, stale или чужая execution operation отклоняется до provider read-back;
- read-back выполняется только через явно зарегистрированный typed verification adapter; отсутствие adapter остаётся fail-closed;
- каждая попытка получает durable Job с exact request hash и idempotency key; повтор того же подтверждённого запроса возвращает уже сохранённый receipt, а переиспользование ключа с другим request material отклоняется;
- provider read-back хранит только certificate/profile/agent/management признаки и время наблюдения; credential values и одноразовые enrollment artifacts в runtime result/evidence не попадают;
- после read-back runtime повторно проверяет тот же execution receipt и Household snapshot; любой drift переводит verification Job в `failed` и не выдаёт managed-state authority;
- отрицательная post-condition проверка является корректно завершённой verification-операцией, но оставляет `managed_state_change_authorized=false`;
- положительная проверка может выдать `managed_state_change_authorized=true` как evidence, однако runtime **не применяет** изменение Household state автоматически: отдельный exact-state commit boundary остаётся обязательным;
- receipt и evidence сохраняются для idempotent lookup, а Audit фиксирует exact provider operation, verification identity и итог без secret material;
- runtime не выдаёт provider mutation, policy application, infrastructure mutation или external publication authority;
- `POST /api/v1/household/devices/enrollment/verification/verify` наследует существующие authentication/same-origin/external-access fences; cross-origin и запрещённые external requests блокируются до runtime;
- без зарегистрированного production verification adapter endpoint возвращает fail-closed ошибку и не способен выполнять внешние provider-запросы.

## Семантика безопасности

Успешный enrollment-result требует одновременного подтверждения всех post-condition:

1. management certificate присутствует;
2. management profile присутствует;
3. management agent присутствует;
4. provider read-back подтверждает активное управление.

Если хотя бы один пункт не подтверждён, `post_condition_verified=false` и `managed_state_change_authorized=false`. Cleanup/de-enrollment/retry planning не может превратить отрицательный verification result в успешный managed-state transition.

## Что этот slice пока не делает

- не добавляет production provider adapter;
- не выполняет сетевые запросы к конкретному MDM без явно зарегистрированного adapter;
- verification HTTP boundary присутствует в source, но по умолчанию fail-closed из-за отсутствия production adapter;
- de-enrollment пока остаётся типизированной plan/confirm/request/result/receipt boundary без durable provider-mutation runtime;
- не разрешает автоматический retry enrollment;
- не применяет `managed=true` автоматически даже после положительного verification evidence;
- не меняет canonical Stable 0.56.0 и статус 0.57.0;
- не запускает CI или release workflow.

## Следующие обязательные части 0.58

- durable de-enrollment Job/Audit runtime с idempotent receipt lookup и crash/restart recovery;
- provider adapter registration/qualification для read-back и de-enrollment;
- exact-state managed-state commit после положительного verification evidence;
- API boundary cleanup/de-enroll/recover без передачи секретов;
- post-cleanup read-back + recovery after restart;
- restart/backup/restore/HA проверки и реальный qualification contour перед присвоением RC.
