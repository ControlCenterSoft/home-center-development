# Home Center 0.58.0

**Статус:** подготовка разработки; не Release Candidate и не Public Stable.

## Цель релиза

0.58.0 закрывает обязательную границу post-condition verification после provider-backed enrollment execution из 0.57.0. Принятие команды провайдером не считается успешным подключением: Home Center должен повторно прочитать фактическое состояние устройства и разрешить `managed=true` только после положительной проверки.

## Подготовленная граница NR2

- точный verification plan привязывается к 0.57 execution receipt, Household snapshot/resource version/generation, устройству, провайдеру и `provider_operation_id`;
- provider observation является только read-only evidence и не получает mutation authority;
- проверяются типизированные признаки `certificate`, `profile`, `agent`;
- набор обязательных признаков задаётся доверенным provider-specific verification profile; неизвестное/отсутствующее обязательное evidence приводит к fail-closed `not-verified`;
- provider state должен быть явно `enrolled`; `unknown`, `not-enrolled` и `cancelled` не считаются успехом;
- только результат `verified` выставляет `post_condition_verified=true`, `enrollment_completed=true` и `managed_state_change_authorized=true`;
- даже при успешной verification остаются закрыты `policy_application_authorized`, `infrastructure_mutation_authorized` и `external_publication_authorized`.

## Что эта подготовка намеренно не делает

- не изменяет `ManagedDevice.managed` непосредственно;
- не применяет PolicyBundle/EffectivePolicy;
- не выполняет provider mutation;
- не читает значения секретов;
- не запускает de-enrollment;
- не объявляет релиз готовым.

## Следующие обязательные шаги 0.58.0

1. интегрировать verification runtime с durable Job/Audit и exact-state revalidation;
2. после положительной проверки выполнить отдельный CAS-переход `ManagedDevice.managed: false -> true` с повторным read-back;
3. реализовать de-enrollment, failed-enrollment cleanup и безопасное восстановление после restart;
4. добавить provider-specific verification adapters/profiles без обхода типизированной границы;
5. закрыть negative/stale/replay/recovery tests и artifact/install/upgrade qualification;
6. только после runner-квалификации точного head продвигать release identity и далее официальный release cycle.

## Совместимость и безопасность

Модель остаётся single-node first и не вводит отдельный обязательный координатор. В multi-node/HA verification должна использовать тот же authoritative durable state и exact generation, а stale state обязан блокировать переход. Никакой результат transport/API вызова не может подменить проверенный post-condition.
