# Home Center 0.58.0

**Статус:** подготовка разработки; не Release Candidate и не Public Stable.

## Цель релиза

0.58.0 закрывает обязательную границу post-condition verification после provider-backed enrollment execution из 0.57.0. Принятие команды провайдером не считается успешным подключением: Home Center должен повторно прочитать фактическое состояние устройства и разрешить `managed=true` только после положительной проверки.

## Подготовленная граница NR2

- точный verification plan привязывается к 0.57 execution receipt, Household snapshot/resource version/generation, устройству, провайдеру и `provider_operation_id`;
- provider observation является только read-only evidence и не получает mutation authority;
- проверяются типизированные признаки `certificate`, `profile`, `agent`;
- набор обязательных признаков задаётся доверенным provider-specific verification profile; неизвестное/отсутствующее обязательное evidence приводит к fail-closed `not-verified`;
- provider state должен быть явно `enrolled`; `unknown`, `not-enrolled` и `cancelled` не считаются успехом;
- только результат `verified` выставляет `post_condition_verified=true`, `enrollment_completed=true` и `managed_state_change_authorized=true`;
- даже при успешной verification остаются закрыты `policy_application_authorized`, `infrastructure_mutation_authorized` и `external_publication_authorized`.

## Второй NR2-проход: exact managed-state CAS

Подготовлена отдельная граница перехода продуктового Household state после положительной verification:

- переход принимает только типизированный `verified` result, где `post_condition_verified=true` и `managed_state_change_authorized=true`;
- перед изменением повторно сверяются точные `snapshot_id`, `resource_version`, `generation`, устройство и FamilyMember;
- изменение может подтвердить только Household actor с `administration_allowed=true`;
- меняется ровно один `ManagedDevice.managed: false -> true`; остальные Household данные сохраняются;
- результат формируется через существующий optimistic-concurrency `build_household_replacement`, поэтому durable runtime обязан записывать его только с исходным `resource_version` как CAS-precondition;
- повтор против уже `managed=true` без сохранённого matching receipt блокируется fail-closed: система не имеет права угадывать, что состояние получено именно этим enrollment;
- даже после успешного перехода остаются закрыты policy application, provider mutation, infrastructure mutation и external publication;
- добавлены machine-readable plan/receipt contracts и negative/stale/replay/authorization tests для последующей runner-квалификации.

Эта подготовка не применяет результат к production store сама по себе и не обходит будущую durable Job/Audit/recovery интеграцию.

## Третий NR2-проход: trusted verification profiles и failed-enrollment cleanup

Устранена ещё одна fail-closed граница перед runtime-интеграцией:

- обязательные `certificate` / `profile` / `agent` checks больше не должны определяться входным пользовательским запросом: подготовлен controller-owned trusted verification profile и закрытый profile catalog;
- profile identity и catalog identity детерминированы содержимым, один provider может иметь ровно один активный verification profile в конкретном catalog snapshot;
- неизвестный provider без доверенного profile блокируется fail-closed до чтения provider evidence;
- profile/catalog являются read-only policy evidence и не разрешают provider mutation, secret access, `managed=true`, policy application, infrastructure mutation или external publication;
- для `not-verified` результата подготовлен отдельный failed-enrollment cleanup plan: `provider-state-unknown` требует повторного наблюдения, `provider-not-enrolled` не требует provider cleanup, а enrolled-состояние с отсутствующим обязательным evidence требует отдельного de-enrollment workflow;
- даже если de-enrollment требуется, cleanup plan сам не разрешает provider mutation и не разрешает автоматический retry; destructive/remote cleanup должен быть отдельно подтверждён, выполнен типизированным adapter и затем повторно проверен;
- добавлены закрытые machine-readable contracts и negative tests, сохраняющие `retry_authorized=false` и все не относящиеся к cleanup authority в false.

## Что эта подготовка намеренно не делает

- не применяет PolicyBundle/EffectivePolicy;
- не выполняет provider mutation;
- не читает значения секретов;
- не запускает de-enrollment автоматически;
- не разрешает автоматический повтор enrollment после ошибки;
- не объявляет релиз готовым.

## Следующие обязательные шаги 0.58.0

1. интегрировать verification runtime и managed-state transition с durable Job/Audit, idempotent receipt lookup и exact-state revalidation при фактическом store commit;
2. связать cleanup plan с отдельно подтверждаемым de-enrollment adapter, повторной post-condition verification, safe retry gate и безопасным восстановлением после restart;
3. добавить provider-specific observation adapters поверх уже закрытого trusted verification profile/catalog boundary;
4. закрыть оставшиеся negative/stale/replay/recovery tests и artifact/install/upgrade qualification;
5. только после runner-квалификации точного head продвигать release identity и далее официальный release cycle.

## Совместимость и безопасность

Модель остаётся single-node first и не вводит отдельный обязательный координатор. В multi-node/HA verification, cleanup и managed-state CAS должны использовать один authoritative durable state и exact generation; stale state обязан блокировать переход. Никакой результат transport/API вызова не может подменить проверенный post-condition. Никакой failed-enrollment cleanup не должен автоматически повторять provider execution.
