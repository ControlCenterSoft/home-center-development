# Home Center 0.58.0 — development notes

Status: **development only**. This document does not declare RC or Stable readiness.

Home Center 0.58 extends the qualified 0.57 enrollment-execution boundary with fail-closed
post-condition verification, explicit safe de-enrollment and bounded failed-enrollment cleanup.

Implemented in the current development slices:

- closed Draft 2020-12 schemas for enrollment verification request/read-back/evidence/receipt;
- exact enrollment verification binding to plan/provider operation/device/member/execution generation;
- bounded freshness checks and content-addressed verification evidence;
- deterministic de-enrollment plan bound to successful verification evidence and current Household
  snapshot/resource-version/generation;
- separate de-enrollment confirmation before provider mutation and explicit provider read-back after
  de-enrollment; only fresh exact-bound `unmanaged`/`absent` evidence can authorize a later local
  managed-state transition;
- failed-enrollment cleanup contracts that permit only bounded transient cleanup after read-back and
  escalate provider `managed` state to explicit de-enrollment;
- on the isolated non-runner NR1 integration branch, authenticated verification plan/confirm API
  wiring with Household parent/RBAC revalidation, durable idempotent Jobs and Audit evidence;
- scoped re-authentication before verification execution using a short-lived, actor/scope-bound,
  single-use in-memory step-up grant; grants deliberately disappear on restart/failover;
- observational verifier-adapter registration requires `verification_read_only=true`; absence of a
  concrete adapter fails closed before a verification Job is created;
- verified evidence is persisted before Home Center may build a new Household snapshot with
  `ManagedDevice.managed=true`; exact snapshot/resource-version/generation drift is rejected;
- the local managed-state write is followed by durable Household read-back. A failed read-back
  restores the validated base Household state rather than reporting success;
- restart recovery can finalize an already durable `verified-pending-apply` transition without
  repeating the provider read-back or any provider mutation;
- runtime HTTP boundary advances to API v4 only on that isolated branch; the 0.57 API remains its
  parent and all same-origin/external-access/session fences are preserved;
- no automatic provider retry after unknown/ambiguous outcomes;
- secret values, policy mutation, device-record removal, infrastructure mutation and external
  publication remain outside these boundaries.

Still not implemented, integrated, qualified or claimed:

- concrete production provider verifier/adapter and provider qualification;
- merge of the NR1 runtime/API wiring into the shared 0.58 integration branch;
- runner qualification of the NR1 runtime/API wiring (the branch is intentionally kept without a PR
  and outside `main`/`release/**` so this non-runner development stream does not start GitHub Actions);
- production de-enrollment/cleanup runtime Job/API wiring beyond the already implemented contracts;
- 0.58 release packaging, backup membership, install/upgrade/rollback qualification;
- real target-node and multi-node HA/restart acceptance;
- RC/Public Stable promotion;
- commercial/legal clearance.

Public Stable remains 0.56.0 until the authoritative release gates are closed. The 0.57 release
candidate path remains separate and is not re-qualified by this 0.58 development work.
