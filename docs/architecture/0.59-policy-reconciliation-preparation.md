## Boundary

`household_policy_reconciliation.py` introduces a transport-neutral, read-only verification contract for a future concrete policy backend:

- exact binding to Household/member, protected Desired State generation, originating policy-change plan, policy identity and SHA-256;
- content-addressed reconciliation request identity;
- read-only backend observation with closed states `enforced`, `not-enforced`, `unknown`, `ambiguous`;
- controller-owned trusted time boundary with a bounded observation age;
- no endpoint, credential, secret, shell, filesystem, network or provider mutation surface in the domain module;
- `enforcement_verified=true` only for a fresh exact-bound `enforced` observation whose actual policy digest exactly equals the desired policy digest;
- digest mismatch, not-enforced, unknown and ambiguous results stay `reconciliation_required=true` and never claim success;
- evidence explicitly records that backend/infrastructure/external-publication mutation was not performed.

Three closed Draft 2020-12 schemas define the request, read-back observation and verification evidence.

## Follow-up integration requirements

1. Compose a separate `HouseholdPolicyReconciliationRuntimeService`; do not add provider execution to the Policy Composer commit path.
2. Register only explicitly read-only backend adapters. The adapter must receive the closed reconciliation request and return only the closed observation object.
3. Persist reconciliation Job/Audit/evidence before changing Home Center's verification flag.
4. Re-read the exact protected Desired State immediately before accepting evidence. Generation, `plan_id`, `policy_id` and `policy_sha256` must still equal the request binding.
5. Only after verified evidence may product Desired State move from `{enforcement_verified:false,reconciliation_required:true}` to `{enforcement_verified:true,reconciliation_required:false}`. This product-state transition must not imply infrastructure mutation authority and must be followed by a StateStore read-back.
6. If verification is pending/mismatch/blocked, preserve Desired State unchanged. Do not automatically invoke a backend or retry a mutation.
7. Extend the Desired State schema/runtime parser carefully: the current Policy Composer state intentionally accepts only the unverified state. A verified variant must require immutable reconciliation evidence identity/digest so a caller cannot flip two booleans directly.
8. API exposure, if added, must reuse existing authenticated session, parent/admin server-side binding, same-origin/CSRF and idempotency fences. A read-only reconcile check itself must not grant backend mutation authority.
9. Backup/restore qualification must preserve the latest verified evidence and must not turn an unverified restored Desired State into verified state.
10. Concrete backend enforcement remains a separate slice. This layer verifies Actual State; it does not implement policy application.

## Qualification expectations

The focused domain tests cover exact success, policy digest mismatch, not-enforced, unknown/ambiguous, stale/future observations, request/backend/binding substitution, desired-state tamper, already-verified replay rejection, required actual digest, max-age bounds and UTC-only timestamps. Normal PR-triggered Home Center CI/privacy/infrastructure-neutrality qualification is required for the exact branch head; no workflow dispatch, synthetic load or unchanged rerun is required.
