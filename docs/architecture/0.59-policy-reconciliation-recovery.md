# Home Center 0.59 — Policy reconciliation crash recovery

Status: **non-runner development slice; prepared for later qualification; no production authority**.

Base identity: `ControlCenterSoft/home-center-development` PR #171 exact head `8ce6b6fa9d531e4d336b41b5c70f167c19c67b2f`. Public Stable remains 0.56.0; the allowed development horizon remains 0.57 / 0.58 / 0.59 and 0.57 remains the nearest Release Candidate path.

## Problem closed by this slice

The 0.59 read-only reconciliation runtime persists exact reconciliation evidence before it marks the durable Job successful, and only after Job success writes the terminal reconciliation envelope. A process interruption can therefore occur at either of two durable boundaries:

1. `evidence persisted -> [process loss] -> Job still verifying`;
2. `evidence persisted -> Job succeeded -> [process loss] -> terminal envelope not written`.

Repeating the backend read after restart is unnecessary and can produce a different observation. Treating incomplete durable state as success without exact revalidation would also be false success.

This slice adds a separate `HouseholdPolicyReconciliationRecoveryService` for both interruption boundaries.

## Recovery contract

Recovery acts only on reconciliation envelopes whose durable status is `evidence-persisted`.

Before completion it fail-closed validates:

- deterministic reconciliation request identity and closed request contract;
- exact persisted reconciliation evidence, request/backend/binding identity and non-mutation assertions;
- exact protected Desired State digest;
- Desired State generation, originating plan, policy identity and policy SHA-256;
- Desired State still remains `enforcement_verified=false` and `reconciliation_required=true`;
- durable Job belongs to the reconciliation action and carries the same idempotency identity.

If the Job is still `verifying`, recovery may finish that Job with explicit recovery evidence. If the Job is already `succeeded`, recovery first verifies that its completion evidence contains the same immutable reconciliation evidence and proves `backend_reinvoked=false` / `desired_state_transition_performed=false`; only the missing terminal envelope is then reconstructed.

## Safety invariants

Recovery never:

- invokes the backend adapter again;
- executes or retries policy enforcement;
- changes protected Desired State verification flags;
- mutates Household, network, filesystem, provider or infrastructure state;
- grants external-publication authority;
- converts stale or ambiguous state into success.

Recovery-created Job evidence explicitly records `backend_reinvoked=false`, `desired_state_transition_performed=false` and `recovered_after_interruption=true`. When the original runtime had already completed the Job, its existing immutable completion evidence is validated rather than replaced.

If exact Desired State or Job identity drifted, recovery is blocked. The original already-persisted reconciliation evidence is preserved for audit/diagnostics and a separate `recovery_failure` is recorded instead of overwriting that evidence.

## Backup / restore semantics

Because reconciliation envelope, evidence, protected Desired State and Job live in StateStore, `StateStore.backup_to()` must preserve an interrupted `evidence-persisted` state. After restore, the same recovery validation is applied against the restored exact Desired State and Job. Restore never upgrades an unverified Desired State to verified merely because verified read-only evidence exists.

The accompanying tests cover:

1. interruption immediately after evidence persistence and safe completion without a second backend read;
2. interruption after durable Job success but before terminal envelope persistence, again without a second backend read;
3. fail-closed recovery when Desired State drifts, while preserving the original evidence;
4. backup/restore of an interrupted reconciliation and safe completion after restore, still without backend reinvocation.

These tests are source-prepared only in this non-runner stream and have not been promoted as qualification evidence.

## Remaining 0.59 boundary

This slice deliberately does **not** implement the next protected verification-state transition. Moving product Desired State from `{enforcement_verified:false,reconciliation_required:true}` to `{enforcement_verified:true,reconciliation_required:false}` must remain a separate exact-bound transition that consumes immutable reconciliation evidence, performs a protected CAS/read-back, remains recoverable, and grants no backend/infrastructure/publication authority.

Public API wiring, concrete backend mutation/enforcement, a production-qualified backend adapter and commercial/legal clearance also remain separate 0.59 work.
