# Home Center 0.58 — post-condition verification and safe de-enrollment

Status: development contract/runtime slice; **not Release Candidate and not Public Stable**.

This layer extends the provider-neutral Home Center 0.57 enrollment-execution boundary. Provider
command acceptance is never treated as proof of enrollment or de-enrollment success. State-changing
authority is granted only after a fresh, exact-bound provider/device read-back.

## Enrollment post-condition verification

The verification contract binds the execution plan, provider operation, device, member and execution
generation. A `verified` receipt is the only path that can authorize `managed=true`; a rejected
receipt remains fail-closed and requires recovery/cleanup. Evidence is content-addressed, closed
schemas reject extra fields, and secret values are never part of verification payloads.

The NR1 runtime wiring keeps the full mutation path explicit:

`session -> Household actor binding -> parent/RBAC -> plan -> scoped re-auth -> durable Job -> read-only provider read-back -> contract verification -> durable evidence -> Household optimistic replacement -> Household read-back -> Audit`.

The re-auth grant is short-lived, actor/scope-bound and single-use. It is intentionally memory-only;
restart or failover discards unused grants and therefore requires another credential check instead of
silently extending authority. Passwords and step-up tokens are never written to durable Job/Audit
state.

Verifier adapters are observational only. Registration requires an explicit
`verification_read_only=true` capability and the runtime has no concrete verifier registered by
default. Missing verifier capability fails closed before a new verification Job is created.

After a positive verification receipt, Home Center persists the verified evidence before constructing
the next deterministic Household snapshot. The write is permitted only against the exact previously
validated snapshot/resource-version/generation. The new state is read back immediately; mismatch
restores the base Household state and cannot be reported as success. A restart between verification
and local apply may finalize the already durable verified transition without contacting the provider
again.

## Explicit de-enrollment

De-enrollment is a separate workflow. Its deterministic plan is bound to the exact successful
enrollment verification evidence plus the current Household snapshot/resource version/generation.
A separate confirmation is required before a provider mutation may be attempted.

Provider acceptance/completion is not final success. After provider execution, Home Center must
perform a fresh read-only provider/device read-back. Only exact-bound `unmanaged` or `absent`
evidence can authorize the local managed-state transition. `managed`, `unknown`, `ambiguous`,
stale, future or mismatched evidence is fail-closed. Automatic retry after an ambiguous provider
mutation is forbidden.

The de-enrollment contract does not authorize policy mutation, device-record removal,
infrastructure mutation, external publication or credential-value access.

## Failed-enrollment cleanup

A rejected enrollment verification can produce an explicit cleanup plan. Cleanup always begins
with read-only provider verification:

- provider `managed` -> local cleanup is blocked and the flow escalates to explicit de-enrollment;
- provider `unmanaged` or `absent` -> only bounded transient enrollment state / one-time reference
  cleanup may be authorized;
- provider `unknown` or `ambiguous`, stale/future evidence, or binding mismatch -> no cleanup.

Cleanup never changes `ManagedDevice`, provider state, policy or the durable device record.

## Current integration boundary

The runtime/API wiring is prepared on the isolated branch
`nr1/0.58-runtime-wiring-20260912-b1`, based on the exact current 0.58 contract head. It is kept
without a pull request and outside `main`/`release/**` so the non-runner stream does not start the
repository's GitHub Actions triggers. It therefore remains **prepared code, not qualified code**.

Remaining 0.58 work includes a concrete production verifier adapter and provider qualification,
shared-branch integration followed by the normal hosted qualification flow, production de-enrollment
and cleanup Job/API runtime wiring, release-artifact/backup membership, install/upgrade/rollback
qualification, real target-node acceptance and multi-node HA/restart acceptance. Commercial/legal
clearance is not claimed by this development slice.
