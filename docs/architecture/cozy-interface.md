# Home Center — интерфейс «Уютный» и Household/Intent Layer

Status: ACCEPTED / FUNDAMENTAL ARCHITECTURE DECISION

## 1. Назначение

«Уютный» — обязательный второй интерфейс Home Center. Это не отдельный продукт, не тема оформления и не урезанная редакция Home Center.

Его задача — дать домашнему пользователю максимальный результат при минимальном количестве действий и не заставлять его работать с инфраструктурными сущностями, если для бытового сценария это не требуется.

Главное UX-правило:

> Home Center знает, как устроена инфраструктура. Пользователь говорит только, чего он хочет.

## 2. Два уровня пользовательского интерфейса

Home Center имеет два взаимодополняющих уровня управления:

- **«Уютный»** — mobile-first интерфейс для повседневного домашнего управления; крупные элементы, короткие сценарии, готовые безопасные настройки и отсутствие прямых опасных операций;
- **«Полный»** — профессиональный интерфейс со всеми техническими параметрами, узлами, ролями, сетью, хранилищами, сервисами, политиками, журналами и диагностикой.

«Уютный» не должен дублировать полный UI в уменьшенном виде. Он работает через бытовые намерения и доменные модели верхнего уровня.

## 3. Основные пользовательские сущности

### 3.1. «Домой»

Сводный экран состояния дома. Показывает только то, что полезно для ежедневного управления: состояние домашних сервисов, семьи, интернета/VPN, детских ограничений, умного дома, мультимедиа, игровых сервисов, резервных копий и действительно важных уведомлений.

Технические ошибки должны преобразовываться в понятное состояние и, где это безопасно, сначала проходить автоматическую попытку восстановления.

### 3.2. «Семья»

Человек является основной сущностью, а устройства и политики привязываются к нему.

Обязательные бытовые роли первой версии:

- `parent` — родитель;
- `child` — ребёнок;
- `guest` — гость.

Выбор роли применяет не только RBAC-права, а полный **RolePreset / PolicyBundle**. Создание члена семьи должно требовать минимум данных; остальные поддерживаемые настройки Home Center формирует автоматически.

RolePreset может включать:

- учётную запись и identity binding;
- переносимый профиль и домашние каталоги, если соответствующий provider доступен;
- доступы к домашним ресурсам;
- internet/DNS policy;
- лимиты и расписания;
- VPN policy;
- managed-device policy;
- доступ к мультимедиа и игровым сервисам;
- разрешения умного дома;
- дополнительные provider-specific настройки, скрытые от «Уютного» интерфейса.

Один человек должен иметь одну понятную карточку, из которой видны связанные устройства и итоговая эффективная политика.

### 3.3. «Мой дом»

Бытовое представление домашней инфраструктуры. Базовые разделы:

- Интернет;
- Умный дом;
- Фильмы и музыка;
- Игры;
- Файлы;
- Сервер;
- Резервные копии;
- дополнительные домашние сервисы.

В «Уютном» не должны без необходимости показываться Samba, PostgreSQL, контейнерные runtime, Zigbee2MQTT, TorrServer, WireGuard и иные конкретные технологии реализации. Они остаются backend providers и доступны в полном интерфейсе при наличии соответствующих возможностей.

## 4. Архитектурная цепочка

Каноническая цепочка для «Уютного»:

`Cozy UI → Household/Intent API → Policy Composer → Core API / Desired State → Reconciler / Execution → Actual State → Post-condition verification`

«Уютный» не получает отдельный обходной execution path. Все изменения обязаны сохранять общие Home Center guarantees: authorization, typed actions, idempotency, stale-state protection, audit/evidence, post-condition verification и recovery/rollback semantics.

## 5. Базовая доменная модель

Начиная с foundation-релиза должны быть предусмотрены как минимум следующие сущности или эквивалентные versioned contracts:

- `Household`;
- `FamilyMember`;
- `HouseholdRole`;
- `ManagedDevice`;
- `RolePreset`;
- `PolicyBundle`;
- `EffectivePolicy`;
- `UserIntent`;
- `RecommendedAction`.

Точная физическая реализация может эволюционировать, но эти смысловые границы не должны растворяться в provider-specific конфигурации.

## 6. Safety invariants

Для «Уютного» обязательны следующие правила:

- safe-by-default;
- default deny для неподтверждённых privileged возможностей;
- опасные инфраструктурные операции не выводятся как обычные бытовые действия;
- destructive actions, raw network/storage/node operations и аналогичные expert-функции выполняются только через полный интерфейс и общий protected change workflow;
- автоматическое исправление разрешено только для заранее типизированных, проверяемых и обратимых/восстанавливаемых сценариев;
- пользовательские намерения всегда преобразуются в plan/desired state до изменения инфраструктуры;
- итоговая успешность определяется Actual State и post-condition verification, а не фактом запуска команды;
- effective policy должна быть объяснима уполномоченному пользователю;
- provider failure не должен приводить к молчаливому ослаблению детских или security policies.

## 7. Mobile-first UX

«Уютный» проектируется прежде всего для телефона:

- крупные touch targets;
- одна основная задача на экран;
- минимум полей ввода;
- понятные бытовые формулировки;
- готовые пресеты вместо ручной сборки политик;
- прогрессивное раскрытие деталей;
- отсутствие технических идентификаторов и provider terminology в основном потоке;
- QR/onboarding flows там, где они уменьшают количество ручных действий.

## 8. Гостевой и device onboarding

Целевая модель предусматривает простое приглашение гостя и привязку устройства, в том числе через QR или другой безопасный bootstrap-механизм.

Гостевой доступ должен иметь ограниченный scope и срок действия, когда это применимо. Device onboarding должен автоматически связывать устройство с выбранным FamilyMember и применимой EffectivePolicy без ручной настройки сертификатов, VPN, Wi-Fi/MDM и других низкоуровневых параметров, если соответствующие providers это поддерживают.

## 9. Release boundary

Фактическая пользовательская доступность определяется только официально опубликованной release identity соответствующего канала. Номер development-версии, наличие кода или архитектурного решения сами по себе не означают опубликованный релиз.

- **0.23.0** — опубликованный исходный релиз durable home-service transition scope; «Уютный» в него не входит;
- **0.24.0–0.25.0** — исторические development stages durable transition (read-back verification и completion audit), а не основание объявлять функции «Уютного» опубликованными;
- **с 0.26.0 в development-линии** сформирован Household/Intent foundation. Он является архитектурной основой «Уютного», но конкретная пользовательская возможность доступна только если вошла в фактически опубликованную release identity;
- **0.40.0** — предыдущий официальный canonical/source release; его scope — evidence-only compatibility binding Home Service и он не расширяет пользовательский интерфейс «Уютный»;
- **0.41.0** — предыдущий подтверждённый PUBLIC STABLE baseline; exact-state revalidation этого binding остаётся evidence-only и не расширяет «Уютный»;
- **0.42.0** — текущий официальный canonical/source release и текущий подтверждённый PUBLIC STABLE RELEASE. Versioned requirement-set contract для точных Home Service/API revisions остаётся evidence-only и не расширяет пользовательский интерфейс «Уютный»;
- **0.46.0 и последующие подготовленные development-линии** развивают конкретные экраны и сценарии «Уютного». Они не считаются пользовательски доступными до собственной релизной квалификации и официальной публикации.

Официальный public stable-канал — `ControlCenterSoft/home-center-stable`. Полноценный PUBLIC STABLE RELEASE **0.42.0** подтверждён отдельной public release identity. Канонический tag `v0.42.0` указывает на commit `980e9d84736b64a6e1558bae524e4da2a1c8115a`; public export использует подтверждённый `APPROVED-SOURCE.json` / manifest mapping и поэтому не обязан иметь тот же commit SHA.

## 10. Правило для дальнейшей разработки

Начиная с Household/Intent foundation каждая новая пользовательская capability Home Center должна при проектировании определить:

1. техническое представление в Full/Core API;
2. бытовое представление в Household/Intent API либо явное обоснование, почему оно не применимо;
3. mapping между intent/policy и Desired State;
4. safety gates и permissions;
5. post-condition verification и recovery behavior.

Это правило предотвращает ситуацию, в которой техническая функция сначала проектируется только для expert UI, а затем требует отдельной архитектурной переделки для «Уютного».

## 11. Non-goals

«Уютный» не должен:

- становиться отдельным продуктом или fork Home Center;
- иметь отдельную модель данных, несовместимую с Core;
- обходить RBAC, Change/Job/Audit или Reconciler;
- скрывать критическую неисправность так, чтобы пользователь считал систему исправной;
- автоматически включать external publication, NAT/port-forwarding или другие рискованные функции;
- превращать фиксированные бытовые роли в единственный механизм профессионального RBAC.
