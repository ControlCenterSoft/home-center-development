# Home Center 0.60 — Parental Internet/DNS/Proxy policy foundation

Status: development architecture; **not Release Candidate and not Public Stable**.

The current published Public Stable baseline is 0.57.0. Version 0.60 stays within the permitted three-release product window and does not include 0.61+ capabilities.

## Scope

0.60 introduces a deterministic parental Internet policy for a child member. Policy decisions are bound to:

- exact Household/member identity and the exact verified 0.59 composed-policy state;
- a content-addressed rule source (`rule_source_id`, version and SHA-256);
- explicit domain allow/deny lists;
- explicit category allow/deny lists;
- bounded weekly schedule windows;
- daily and weekly usage quotas;
- continuous-session limit, grace window, mandatory break and bounded daily bonus.

The protected policy workflow uses the common Home Center safety model: plan → explicit confirmation → durable Job → protected Desired State → read-back → Audit/evidence. Saving policy Desired State is not equivalent to applying DNS/proxy rules.

## Fail-closed precedence

Decision order is deterministic and designed so an allow rule cannot bypass parental time controls:

1. exact policy/Household/member binding;
2. exact rule-source version and SHA-256 binding;
3. explicit domain deny;
4. allowed schedule;
5. weekly quota;
6. daily quota including bounded bonus;
7. continuous-session limit including bounded grace and required break;
8. explicit domain allow;
9. category deny / allow;
10. missing classification or unknown allow-list membership → DENY.

For child policy, unavailable classification is not interpreted as safe access. Stale or mismatched rule-source evidence is always DENY. An empty category allow-list is not an allow-all policy.

## Protected Desired State

The 0.60 parental Desired State is accepted only against a current verified 0.59 base policy. It is exact-bound to the Household/member, generation, plan, base-policy identity and SHA-256, rule-source evidence and full parental policy digest.

Every newly committed parental policy starts with:

- `enforcement_verified=false`;
- `reconciliation_required=true`;
- `dns_policy_applied=false`;
- `proxy_policy_applied=false`;
- `infrastructure_mutation_authorized=false`;
- `external_publication_authorized=false`.

Stale Household state, stale or superseded 0.59 verification evidence, mismatched Desired State and conflicting generation fail closed.

## DNS/proxy enforcement adapter boundary

0.60 defines a provider-neutral typed boundary for a future concrete DNS/proxy backend. The adapter registry is empty by default: Home Center does not discover, select or enable an enforcement provider implicitly.

A compatible adapter must explicitly declare DNS, proxy and Actual-State read-back capabilities. The policy profile requires both DNS and proxy enforcement surfaces plus read-back. Rollback capability is separately declared.

The apply request is exact-bound to:

- durable Job identity;
- adapter identity/version;
- Household/member;
- parental Desired State generation and plan;
- full Desired State SHA-256;
- verified 0.59 base-state SHA-256;
- parental policy identity and SHA-256;
- the complete closed child-policy payload.

The payload carries no credential values. External publication is never authorized by this contract.

## Provider acceptance is not success

An adapter apply response only records that the provider accepted an operation. It is hard-bound to:

- `post_condition_verified=false`;
- `enforcement_verified=false`;
- `actual_state_readback_required=true`.

Home Center must not display or persist an enforced-success claim from provider acceptance alone.

## Actual State read-back

Read-back is explicitly non-mutating. Its request grants no backend, infrastructure or external-publication mutation authority.

An observation is accepted only when it matches the exact adapter operation, Desired State digest and parental policy digest. Each DNS/proxy plane is reported as `enforced`, `not-enforced` or `unknown`:

- `enforced` requires the exact observed policy SHA-256;
- `not-enforced` or `unknown` must not carry an enforcement digest and must include a bounded blocker;
- even a fully matching observation remains evidence for a separate verification transition and carries `enforcement_verified=false`.

This prevents an observation object itself from becoming an implicit state-mutation or false-success path.

## Rollback/recovery boundary

Rollback is a separate typed operation bound to the failed Desired State digest, failed policy digest and explicit recovery evidence. Rollback acceptance is not recovery completion.

A rollback result therefore remains:

- `post_condition_verified=false`;
- `rollback_verified=false`;
- `actual_state_readback_required=true`.

Verified recovery requires a subsequent exact Actual-State read-back and a separate protected-state verification transition.

## Contract closure

The public transport contracts are closed Draft 2020-12 schemas. Unknown fields are rejected. The apply payload embeds the complete closed parental-policy shape rather than accepting an arbitrary object; this prevents a transport peer from adding hidden authority fields or weakening `default_decision=deny`, DNS/proxy requirements, rule-source evidence or mutation/publication boundaries.

## UI semantics

«Уютный» must describe household intent and verified state in ordinary language, for example: blocked by schedule, quota exhausted, category blocked, rule source unavailable, or rules saved but still awaiting application and verification.

«Полный» may additionally expose exact rule-source identity, policy/Desired State digests, schedule/quota values, adapter capability state and blocker codes. Both interfaces use the same server-side authorization, exact-state and verification boundaries. Neither view may claim DNS/proxy enforcement before verified Actual State exists.

## Explicit exclusions

0.60 does not, by the presence of these contracts alone:

- register a concrete production DNS/proxy adapter;
- configure DNS, proxy, firewall, routing, browser/device settings or VPN;
- authorize external publication;
- treat provider acceptance as policy enforcement;
- treat rollback acceptance as verified recovery;
- include VPN egress policy. VPN remains a separate later capability and cannot override a stricter parental DENY.

A production enforcement path must add explicit adapter qualification, execution orchestration, protected verification transition, recovery completion and negative-security qualification without weakening the contracts above.
