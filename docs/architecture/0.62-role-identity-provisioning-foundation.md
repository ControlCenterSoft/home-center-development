# Home Center 0.62 — role-driven identity/account provisioning foundation

## Scope

0.62 is within the permitted development horizon after current Public Stable 0.60.0. This slice prepares the typed, fail-closed planning boundary for role-driven local/directory identity provisioning and portable home/profile placement. It is deliberately **plan-only** and does not execute a provider.

The plan binds all future work to one exact state:

- exact Household `snapshot_id`, `resource_version` and generation;
- exact enabled FamilyMember and Household role;
- exact Effective/Composed Policy identity for that member;
- exact provider id/version/type and content-addressed capability evidence;
- canonical account name;
- explicit local/portable choice for home directory and profile.

No implicit provider choice or capability fallback is allowed.

## Emergency administrator isolation

The existing local emergency administrator remains an independent recovery identity. It is not created, renamed, converted, synchronized or permission-managed through role-driven provisioning.

The planning boundary rejects reserved account names `admin`, `administrator` and `root`. Provider evidence must state `emergency_admin_isolated=true`, and both provider evidence and provisioning plans hard-code arbitrary privilege grant/execution authority to false.

A Home Center `parent`/Household administrator is a Home Center product authority. That role does **not** automatically imply operating-system administrator, directory administrator, sudo/root, Domain Admin or equivalent provider privilege.

## Provider capability evidence

A provider capability record is closed and typed. It states only:

- local vs directory provider;
- supported Household roles;
- whether account creation is supported;
- whether portable home and portable profile modes are supported;
- whether later execution can use secret references;
- SHA-256 evidence identity.

Unknown fields and attempts to claim execution authority are rejected. A request for portable home/profile fails closed if the selected provider has not explicitly advertised the corresponding capability. There is no silent downgrade to local storage.

## Plan semantics

A positive plan remains non-authorizing evidence:

- explicit confirmation is still required;
- account-absence/name-conflict preflight is required immediately before future execution;
- post-condition verification is required after future execution;
- credential material is not authorized;
- emergency-admin mutation is not authorized;
- arbitrary privilege grant is not authorized;
- provider execution is not authorized;
- infrastructure mutation and external publication are not authorized.

Plan identity is deterministic and content-addressed. Strict reconstruction rejects field tampering and cross-plan reuse.

## Cozy / Full UI boundary

The Cozy projection may explain that an account plan is ready for confirmation, including whether portable home/profile were requested. It must state that the account is **not created yet** and that the emergency administrator is unchanged.

The Full projection exposes the exact technical plan and explicitly reports provider execution and credential material as `not-authorized`.

## Follow-up boundaries

Future 0.62 work may add a separate confirmation-gated execution layer only after it revalidates the exact current Household/policy/provider state. That layer must use a typed adapter, secret references rather than credential values, a durable Job/Audit path, exact account-absence/conflict preflight, read-back and post-condition verification before success.

This foundation adds no public mutation endpoint, no concrete production identity provider registration, no HA claim and no commercial-launch clearance. Those remain separate qualification/activation boundaries.
