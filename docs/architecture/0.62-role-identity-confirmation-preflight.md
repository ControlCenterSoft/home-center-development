# Home Center 0.62 — identity confirmation and account preflight

## Purpose

This slice extends the already-qualified 0.62 role-driven identity planning foundation with two additional fail-closed boundaries that are required before any future account creation can be admitted:

1. explicit user confirmation of the exact provisioning plan;
2. fresh read-only evidence that the exact target account name is absent at the exact selected provider.

It deliberately does **not** execute a provider. A positive result means only `confirmed-awaiting-execution`.

## Exact-state revalidation

Confirmation revalidates the complete provisioning plan against the current authoritative state instead of trusting a previously serialized plan:

- exact Household snapshot, resource version and generation;
- exact enabled member and Household role;
- exact Effective/Composed Policy identity;
- exact provider id, version, kind and content-addressed capability evidence;
- exact canonical account name;
- exact local/portable home-directory and profile choices.

The plan is reconstructed through the existing strict 0.62 parser even when the caller supplies an in-memory plan object. This prevents a caller from bypassing canonical/content-addressed validation by constructing a dataclass directly.

Any Household, policy, member, provider or capability drift causes confirmation to fail closed as stale evidence.

## Account-absence preflight

The preflight contract is read-only and content-addressed. It contains only:

- exact provider identity/version/evidence SHA-256;
- exact target account name;
- one bounded observation: `absent`, `exists` or `unknown`;
- UTC observation timestamp;
- hard-false credential, emergency-admin and execution authority flags.

Confirmation accepts only `absent`. `exists` is an explicit account-name conflict. `unknown` is never treated as absence.

The observation must be fresh. The maximum accepted age is five minutes and callers may request a stricter positive limit. Future-dated evidence is rejected. Freshness is evaluated again at confirmation time.

## Security boundary

Neither preflight nor confirmation may expose or authorize credential values. The existing emergency local administrator remains independent and unchanged. Reserved account names remain rejected by the underlying plan contract.

A confirmation receipt explicitly keeps all of the following false:

- provider execution authority;
- credential-material authority;
- emergency-admin mutation authority;
- arbitrary privilege-grant authority;
- infrastructure mutation authority;
- external-publication authority.

Post-condition verification remains mandatory for any later execution boundary.

## Replay and tamper resistance

Preflight evidence and confirmation receipts use deterministic content-addressed identities. Strict reconstruction rejects unknown fields, altered timestamps, altered authority flags and mismatched identifiers.

The same unchanged exact inputs produce the same confirmation receipt. This gives the later durable execution layer stable admission evidence without creating a second or implicit execution request.

## Cozy / Full UI semantics

The Cozy UI may state that the requested account setup has been confirmed and passed a recent account-name availability check, but must also state that the account has **not been created yet**.

The Full UI may expose the exact plan/provider/preflight identities and freshness timestamp. It must show provider execution as `not-authorized` until a separate typed execution boundary exists and succeeds through read-back/post-condition verification.

## Remaining 0.62 boundaries

Before 0.62 can claim actual role-driven account provisioning, separate work is still required for:

- typed provider execution request/result contracts;
- secret-reference-only credential/bootstrap material handling where the exact provider supports it;
- durable Job/Audit/idempotency around execution;
- provider result ambiguity handling with no unsafe automatic retry;
- account/home/profile read-back and post-condition verification;
- recovery/cleanup semantics for partial provider outcomes;
- supported concrete local/directory provider adapters and their exact qualification evidence;
- install/upgrade/artifact/security/release qualification for the final 0.62 identity.

No HA, generic shell, broad directory-administrator authority or commercial-launch clearance is implied by this slice.
