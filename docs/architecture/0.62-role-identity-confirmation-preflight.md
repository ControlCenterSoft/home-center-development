# Home Center 0.62 — identity confirmation, typed execution and verification boundaries

## Purpose

This non-runner source slice extends the already-qualified 0.62 role-driven identity planning foundation with the fail-closed boundaries required around future account creation:

1. explicit confirmation of the exact provisioning plan;
2. fresh read-only account-absence/name-conflict evidence;
3. a narrowly typed provider create-account request that carries only secret references, never secret values;
4. provider-acceptance evidence that explicitly remains unverified;
5. separate fresh read-back and post-condition verification before account creation can be reported as successful.

The slice prepares contracts and domain logic only. It does not register or invoke a production provider and it does not add a public mutation endpoint.

## Exact-state revalidation

Confirmation and provider-request preparation revalidate the complete provisioning plan against the current authoritative state instead of trusting a previously serialized plan:

- exact Household snapshot, resource version and generation;
- exact enabled member and Household role;
- exact Effective/Composed Policy identity;
- exact provider id, version, kind and content-addressed capability evidence;
- exact canonical account name;
- exact local/portable home-directory and profile choices.

Plan and confirmation objects are passed back through their strict public reconstruction paths even when the caller supplies in-memory dataclass objects. This prevents direct object construction from bypassing canonical/content-addressed validation.

Any Household, policy, member, provider or capability drift fails closed before provider request evidence can be built.

## Account-absence preflight

The preflight contract is read-only and content-addressed. It contains only:

- exact provider identity/version/evidence SHA-256;
- exact target account name;
- one bounded observation: `absent`, `exists` or `unknown`;
- UTC observation timestamp;
- hard-false credential, emergency-admin and execution authority flags.

Confirmation accepts only `absent`. `exists` is an explicit account-name conflict. `unknown` is never treated as absence.

The observation must be fresh. The maximum accepted age is five minutes and callers may request a stricter positive limit. Future-dated evidence is rejected. Freshness is evaluated again at confirmation time.

## Confirmation semantics

A positive confirmation receipt means only `confirmed-awaiting-execution`. It explicitly keeps all of the following false:

- provider execution authority;
- credential-material authority;
- emergency-admin mutation authority;
- arbitrary privilege-grant authority;
- infrastructure mutation authority;
- external-publication authority.

The receipt is deterministic and content-addressed. Unknown fields, altered authority flags, binding drift and receipt-ID tampering are rejected.

## Typed provider create-account boundary

The next prepared boundary converts the exact revalidated plan plus exact confirmation into a typed provider request. This is the first boundary that may state `identity_account_creation_authorized=true` and `provider_execution_authorized=true`, but only for the exact account operation represented by that request.

It does **not** authorize generic infrastructure mutation, arbitrary privilege grants, emergency-admin changes or external publication.

Credential/bootstrap inputs are represented only as bounded `secret://...` references. Raw password/token values and path traversal are rejected. If credential references are required but the exact provider capability does not advertise secret-reference support, request construction fails closed.

The provider result contract treats command acceptance only as `state=accepted`. It hard-codes all verification fields to false and forbids credential material from being returned.

## Read-back and post-condition verification

Provider acceptance is not success. A separate read-only observation must bind to the same provider operation, exact provider identity/evidence and exact account name.

The observation carries only bounded states:

- account: `present | absent | unknown`;
- home directory: `ready | missing | unknown`;
- profile: `ready | missing | unknown`.

It is content-addressed, read-only, credential-free and fresh for at most five minutes. Future or stale observations fail closed.

A verified receipt is produced only when all three post-conditions are confirmed: account present, home directory ready and profile ready. `absent`, `missing` and `unknown` never become success. The verified receipt still does not grant emergency-admin, arbitrary privilege, generic infrastructure or external-publication authority.

## Cozy / Full UI semantics

The Cozy UI may say that setup has been confirmed and is waiting for account creation. It must never convert provider acceptance into "account created". Only a later verified post-condition receipt may support an explicit success state.

The Full UI exposes exact plan/confirmation/provider operation/read-back identities and distinguishes `not-authorized`, `accepted-unverified` and `verified` states.

## Remaining 0.62 boundaries

Before 0.62 can be considered an actual supported provisioning release, separate work is still required for:

- durable Job/Audit/idempotency around provider invocation and verification;
- immediate account-conflict revalidation at the durable mutation boundary;
- timeout/transport ambiguity handling with no unsafe automatic retry;
- restart recovery without implicit duplicate provider invocation;
- recovery/cleanup semantics for partial provider outcomes;
- supported concrete local/directory provider adapters and exact qualification evidence;
- public authenticated API/UI wiring through existing authorization/re-auth/origin protections;
- install/upgrade/artifact/security and final release qualification for the exact 0.62 identity.

No HA, generic shell, broad directory-administrator authority or commercial-launch clearance is implied by this source preparation.
