## Goal

Close the next non-runner part of Roadmap 0.63 after the plan-only QR invitation foundation: make invitation state durable and one-time without allowing the QR layer itself to create accounts, register devices, mark devices managed, execute providers or mutate infrastructure.

## Durable state

`QrOnboardingRuntimeRecord` binds one invitation to:

- exact Household `snapshot_id`;
- exact Household `resource_version`;
- exact Household `generation`;
- exact target `FamilyMember`;
- content digest of the immutable invitation evidence;
- monotonic runtime record version;
- active / consumed / revoked state, with expiry derived from bounded invitation time.

Only the SHA-256 digest of the ephemeral onboarding code is persisted. The raw code exists only in `QrOnboardingIssueResult.payload` for immediate QR/user presentation. The combined issue result intentionally has no durable serializer.

## Guest and device boundaries

The runtime layer is intentionally stricter than the generic foundation contract.

Guest issuance currently requires:

- issuer is an enabled parent from the exact Household snapshot;
- target is an existing enabled `guest` member;
- scope is exactly `internet.guest`;
- no device binding is accepted.

Device issuance currently requires:

- target is an existing enabled Household member;
- the specified device already exists in Household and belongs to that member;
- the device is still `managed=false`;
- guest scopes are absent.

This keeps account creation and initial device registration outside QR onboarding and reuses the existing typed Household/device lifecycle.

## Transaction and replay safety

`SQLiteQrOnboardingRuntimeRepository` prepares canonical migration SQL but does not self-install it in production. Integration must add the SQL through the normal migration mechanism; already-published migrations remain immutable.

Consume/revoke transitions use all of:

- exact expected record version;
- `state='active'` conditional update;
- single SQLite transaction;
- content-addressed idempotency key digest rather than raw client idempotency material;
- request digest comparison on replay;
- durable operation receipt stored in the same transaction.

Concurrent/stale transition attempts therefore fail closed. Expiration is a derived temporal state and a read does not silently mutate durable storage.

## No false success

A positive operation receipt verifies only the invitation-state transition. It explicitly emits:

- `invitation_state_post_condition_verified=true`;
- `onboarding_effect_verified=false`;
- account/device/managed/provider/infrastructure/publication authorization = false.

After a successful consume, the next boundary is a separate typed Change/Job:

- guest → `typed-guest-access-change-job`;
- device → `typed-device-binding-change-job`.

Revocation similarly hands off to `typed-access-revocation-change-job` when product state must actually change.

## Audit privacy

`qr_onboarding_audit_details()` accepts only a typed operation receipt and projects bounded identifiers/digests. It cannot receive the QR payload and hard-codes both `raw_onboarding_code_included=false` and `qr_payload_included=false`. The eventual HTTP/runtime integration must write this bounded projection, not request bodies or payloads, into Audit.
