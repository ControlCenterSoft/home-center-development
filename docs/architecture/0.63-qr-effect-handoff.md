## Problem closed by this source slice

A successful QR `consume` or `revoke` proves only the one-time invitation state transition. It does **not** prove that guest access, a device binding, or access revocation was actually applied to authoritative product state. The existing runtime therefore correctly emits `onboarding_effect_verified=false` and names a separate typed Change/Job boundary.

This slice makes that next boundary explicit without executing it.

## Exact effect handoff

`QrOnboardingEffectHandoff` consumes only a typed terminal `QrOnboardingOperationReceipt` and its exact current `QrOnboardingRuntimeRecord`. It re-binds all of the following before it can produce a handoff:

- runtime record and invitation identity;
- invitation evidence SHA-256;
- exact Household snapshot/resource-version/generation;
- target member and subject;
- exact terminal record version and state;
- source receipt digest;
- the `next_required_boundary` already declared by the receipt.

Mappings are closed:

- consumed guest invitation → `typed-guest-access-change-job`;
- consumed device invitation → `typed-device-binding-change-job`;
- revoked invitation → `typed-access-revocation-change-job`.

The handoff cannot grant effect execution, account creation, device registration, managed-state change, provider execution, infrastructure mutation or external publication. It states that an explicit typed Change/Job and later post-condition verification are still required.

## Verification request boundary

`QrOnboardingEffectVerificationRequest` may be created only after a concrete effect Job ID exists. It binds that Job to the exact handoff digest and requests one authoritative post-condition readback:

- guest access → `guest-access-effective`;
- device binding → `device-binding-effective`;
- revocation → `access-revoked`.

The request itself always carries:

- `authoritative_readback_required=true`;
- `post_condition_verified=false`;
- `effect_success_claimed=false`;
- provider/infrastructure/publication authority = false.

Therefore creating or persisting the request can never turn a QR consume/revoke receipt into user-visible success.

## Artifact and contract boundary

Both runtime modules are added to deterministic wheel `REQUIRED_MEMBERS`. Closed Draft 2020-12 schemas reject unknown fields and hard-code non-authorizing flags. Prepared tests cover guest/device/revocation mapping, exact-binding failures, authority-escalation/relabeling attempts, deterministic transport reconstruction and the no-false-success verification request.
