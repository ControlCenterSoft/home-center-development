# Home Center 0.66 — Smart Home device lifecycle foundation

Status: source-only planning/read-model foundation. This document does not claim Release Candidate, Public Stable, provider execution, restore execution or HA readiness.

## Goal

0.66 builds on the exact ZigBee/MQTT inventory and recovery evidence introduced by the 0.65 source line. The first slice adds a provider-neutral device lifecycle model that can distinguish current, stale and unavailable evidence, compare actual room/capability evidence with protected Desired State, and construct exact-bound plans for safe rename and room assignment.

## Desired and Actual State

Desired State contains device identity, monotonic generation, display name, room, canonical expected capabilities and an optional configuration SHA-256. Actual State comes only from an exact content-addressed 0.65 inventory snapshot.

No configuration is treated as verified merely because Desired State contains a digest. The 0.65 inventory deliberately does not expose provider configuration state, so a configured desired digest is reported as `configuration_verification_unavailable` until a later typed provider read-back exists.

## Drift

The lifecycle view uses three drift states:

- `in-sync` only when evidence is current and all evidence available to this layer matches Desired State;
- `drifted` for explicit current-state mismatch such as room/capability mismatch or unavailable configuration verification for a requested digest;
- `unknown` whenever Actual State is stale or unavailable.

Unknown/stale evidence is never projected as healthy or synchronized.

## Change planning

Rename and room-assignment plans are plan-only. They are bound to exact device/coordinator identity, exact inventory SHA-256, Desired State generation and current observed room. Room no-op is rejected. Control characters and unbounded names are rejected. Every plan requires explicit confirmation and grants no execution authority.

A later execution slice must re-read and revalidate the exact current inventory and Desired State before durable admission. The plan itself never invokes a provider and never changes the device.

## Recovery and HA

Configuration recovery remains a separate verified path. The 0.65 verified backup/recovery binding may be consumed by future 0.66 restore planning, but existence of a backup does not authorize restore and does not prove successful recovery.

A physical USB/serial coordinator remains a single physical dependency. Device lifecycle functionality does not convert it into HA. Any future HA claim requires a provider-specific failure/recovery profile and qualification.

## Required follow-up

Full 0.66 requires typed health/diagnostics evidence, provider-backed rename/move/room execution with Identity/RBAC and explicit confirmation, durable Change/Job/Audit, exact authoritative read-back and post-condition verification, configuration restore execution plus verification, restart-safe reconciliation, Cozy/Full projections, backup integration, install/upgrade/rollback qualification and final security/privacy/release gates.
