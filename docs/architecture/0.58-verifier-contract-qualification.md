# Home Center 0.58 — verifier contract qualification

Status: development-only non-runner slice; **not Release Candidate, not Public Stable, not live-provider qualification**.

## Purpose

The 0.58 post-condition runtime already refuses to mark a device managed until a fresh exact-bound read-only provider/device read-back is verified. This slice adds a separate static admission boundary for future concrete read-back adapters so that merely implementing `read_back()` cannot be confused with provider qualification.

The boundary is intentionally narrower than live provider qualification. It proves only that an adapter declares the exact read-only result contract required by Home Center and that its source/profile identity is content-addressable. It does not contact a provider, does not exercise credentials, does not authorize provider mutation and never sets `production_qualified=true`.

## Contract profile

`home-center.device-management-enrollment-verifier-profile.v1` is closed and binds:

- exact `provider_id`;
- verifier implementation identity and revision;
- exact 0.58 post-condition result schema;
- exact signal vocabulary/order: `certificate`, `profile`, `agent`;
- mandatory `verification_read_only=true`;
- SHA-256 source identity.

Unexpected fields are rejected. In particular a caller cannot inject production authority or mutation flags into the profile.

## Qualification receipt

`home-center.device-management-enrollment-verifier-contract-qualification-receipt.v1` is deterministic and content-addressed. Its semantics are deliberately fail-closed:

- `qualification_level=contract-only`;
- `provider_read_performed=false`;
- `production_qualified=false`;
- provider mutation, managed-state mutation, policy mutation, infrastructure mutation and external publication are all false.

A contract receipt is therefore evidence suitable for registry admission and later release qualification, not evidence that a real provider works.

The receipt is revalidated as a closed contract before runtime use. Any unexpected field, authority escalation, provider mismatch, invalid digest, or drift between the registered adapter descriptor and the qualified verifier identity/revision/result contract invalidates the qualification without provider I/O.

## Strict registry wrapper

`ContractQualifiedDeviceManagementEnrollmentPostConditionRuntimeService` wraps the already fail-closed post-condition service. A concrete verifier cannot be registered through this strict registry without a matching qualification profile. Qualification compares the profile against adapter-declared verifier identity/revision/result schema/signals and the existing `verification_read_only=true` capability. The qualification procedure never invokes `read_back()`.

For every verification plan created through the strict wrapper, the exact contract-qualification receipt is copied into the durable verification envelope. Before confirmation, the runtime requires the currently registered adapter to still match that qualification and requires the durable plan binding to equal the current qualification. Descriptor drift or a changed/tampered qualification therefore fails before step-up consumption and before provider read-back. Completed `applied` results remain readable without re-invoking a provider.

This binding is still **contract-only**. It prevents a plan qualified for verifier revision A from silently executing under a different descriptor/revision B, but it cannot prove that a real provider endpoint behaved correctly. That remains a live acceptance gate.

Production composition is intentionally not switched to this wrapper in the non-runner slice. That integration should occur in the normal shared/runner flow together with exact-head qualification, so this task cannot accidentally promote unqualified code or start GitHub Actions.

## Remaining real-provider gate

A concrete production provider is still required. Its acceptance must include at minimum:

1. immutable provider/verifier source identity and legal/commercial metadata;
2. contract qualification receipt from this layer;
3. provider-specific credential/reference handling review without secret values in durable evidence;
4. live read-only enrollment post-condition observations in a controlled target environment;
5. negative observations for stale/future/wrong-device/wrong-operation/ambiguous/not-enrolled states;
6. restart/retry behavior proving no automatic provider mutation after an unknown outcome;
7. real target-node and multi-node acceptance appropriate to the provider;
8. normal exact-head/release qualification before any RC/Stable claim.

Until those gates are satisfied, Home Center must continue to behave as if the concrete verifier is unavailable.
