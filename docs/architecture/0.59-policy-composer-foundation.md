# Home Center 0.59 — Policy Composer foundation

Status: stacked development foundation; **not Release Candidate and not Public Stable**.

This slice implements the runner-qualified core described by the canonical 0.59 work package. It is stacked on the current qualified 0.58 integration lane and does not alter the 0.57 release-candidate path.

## Security model

Policy Composer starts from the existing server-side Household `RolePreset` and may only restrict it. A bundle cannot:

- move internet access to a less restrictive mode;
- enable a capability forbidden by the role;
- clear `managed_device_required=true` from a role that requires management;
- enable external publication.

The actor identity is resolved only from the persisted server-side Household actor binding. Policy changes require an enabled parent/administrator; client-supplied role or authority is never accepted.

## Protected Desired State

A policy change follows:

`Household snapshot -> parent RBAC -> deterministic bundle/composed policy -> immutable plan -> explicit confirmation -> durable Job -> Desired State write -> read-back -> Audit/evidence`.

The plan is bound to the exact Household snapshot/resource version/generation, actor and subject member, current policy digest, observed/expected Desired State generation, bundle and proposed policy digests/material, and reason. Household or Desired State drift rejects confirmation fail-closed.

A successful commit means only that the desired policy was saved. The persisted state and receipt always report:

- `enforcement_verified=false`;
- `reconciliation_required=true`;
- no infrastructure mutation authority/performance;
- no external publication authority/performance.

Therefore Cozy may describe the result as «правила сохранены / ожидают применения», while Full UI may expose the exact technical policy and generation. Neither interface may claim enforcement success from this layer.

## Current boundaries

This slice intentionally does not expose new public HTTP routes and does not implement policy backend enforcement. API exposure must reuse existing authentication, same-origin/CSRF, scoped re-auth and idempotency fences. A separate typed reconciliation/Actual State verifier is required before any future `enforcement_verified=true` state is possible.

Commercial/legal clearance is not implied. The existing module legal/compliance evidence and advisory clearance model remains fail-closed and non-authorizing. Public Stable remains 0.56.0; 0.57 still has priority for RC and its remaining gates are real target/HA/provider qualifications rather than missing hosted tests.
