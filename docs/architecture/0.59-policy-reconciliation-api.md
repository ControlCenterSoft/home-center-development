# Home Center 0.59 — read-only Policy Reconciliation HTTP boundary

Status: runner-qualification integration candidate; not RC, not Stable, not production-qualified.

## Purpose

This slice wires the already implemented 0.59 read-only Household policy Actual State reconciliation service into the Home Center HTTP boundary without adding enforcement or mutation authority. It is composed after the already-qualified V6 effective-policy read model so both read-only surfaces remain available.

The route is intentionally narrow:

- `POST /api/v1/household/policy/reconciliation`;
- authenticated Home Center actor required;
- existing request classification and external-access fence preserved;
- same-origin POST required;
- bounded JSON request body;
- explicit `Idempotency-Key` required;
- underlying Household parent/admin authorization remains server-side;
- only explicitly registered read-only reconciliation adapters are accepted by the underlying runtime.

## Request contract

The JSON body uses schema `home-center.household-policy-reconciliation-http-request.v1` and contains exactly:

- `member_id`;
- `backend_id`;
- `max_observed_age_seconds` in the range 1..900.

The selected Desired State, generation, plan identity and policy digest are resolved and revalidated server-side by the underlying reconciliation runtime. The client cannot supply or override those protected bindings.

## Persistent HTTP idempotency fence

The HTTP facade stores a durable idempotency envelope before invoking reconciliation.

Properties:

- identity is bound to actor + client idempotency key;
- the raw client idempotency key is never persisted; only its SHA-256 is stored;
- request material is hash-bound to the actor;
- same key + same request returns the stored terminal completion without invoking reconciliation again;
- same key + different request fails closed as an idempotency conflict;
- a persisted failed attempt is not automatically retried;
- an uncertain/in-progress attempt is not automatically reinvoked after a retry request.

The last two rules deliberately prefer explicit recovery over possible duplicate provider read-back after an interrupted HTTP request. This preserves the existing no-implicit-replay boundary.

## Authority boundary

This route does **not** authorize or perform:

- protected Desired State mutation;
- policy backend mutation/enforcement;
- infrastructure, network or filesystem mutation;
- external publication;
- creation of a production provider adapter;
- commercial/legal promotion;
- release/RC/Stable promotion.

A successful response only reports the terminal result of read-only Actual State reconciliation and its durable evidence. It does not itself grant enforcement authority.

No re-auth/step-up grant is consumed by this read-only route. Any future policy mutation/enforcement boundary remains a separate privileged operation and must preserve the existing re-auth/step-up, plan/confirm, idempotency, stale-state, Job/Audit, post-condition and recovery requirements.

## Composition

`Runtime` composes:

1. `HouseholdPolicyReconciliationRuntimeService` — existing exact-bound read-only reconciliation runtime;
2. `HouseholdPolicyReconciliationApiService` — persistent HTTP idempotency facade;
3. `RuntimeRequestHandlerV6` — existing effective-policy GET projection;
4. `RuntimeRequestHandlerV7` — reconciliation POST fence layered over V6.

The web server selects `RuntimeRequestHandlerV7`; all non-reconciliation POST routes delegate through V6 to V5, while V6's effective-state GET route remains unchanged.

No concrete reconciliation adapter is registered by this slice. Without an explicitly registered read-only adapter, reconciliation remains fail-closed with `household_policy_reconciliation_adapter_unavailable`.

## Validation scope

Runner qualification checks:

- HTTP replay does not reinvoke the underlying reconciliation runtime;
- idempotency-key reuse with different request material is rejected;
- failed attempts are not automatically reinvoked;
- missing or malformed idempotency keys are rejected before runtime invocation;
- the new route is explicitly scoped and remains separate from 0.58 mutation routes;
- V7 preserves the already-qualified V6 effective-state GET handler;
- complete repository CI, reproducible artifact, privacy and infrastructure-neutrality gates remain green on the exact integrated head.
