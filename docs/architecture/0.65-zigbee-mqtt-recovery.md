# Home Center 0.65 — ZigBee/MQTT backup and recovery boundary

Status: source-only evidence/planning foundation. This document does not claim Release Candidate, Public Stable, provider qualification or HA readiness.

## Goal

Pairing and unpairing must never enter a future mutation path without a recoverable pre-operation state. This slice therefore adds a separate content-addressed backup-evidence boundary and an exact recovery binding between a pair/unpair operation plan and a verified coordinator-configuration backup.

## Backup evidence

A backup record contains only bounded evidence: backup identity, exact coordinator identity, source inventory SHA-256, configuration SHA-256, backup artifact SHA-256 and timestamps. Raw ZigBee network configuration, network keys, broker credentials, pairing codes, tokens or other secret values are not modeled or persisted by this contract.

`verification=verified` requires both configuration and artifact digests plus a bounded verification timestamp. `failed` and `unknown` remain fail-closed and cannot become restore-eligible evidence. A stale or unavailable inventory snapshot cannot produce a usable backup record.

## Recovery binding

A recovery binding is created only when a verified backup matches the exact coordinator and exact inventory digest of the planned pair/unpair operation. The binding is deterministic and content-addressed. Any inventory drift, coordinator mismatch or non-verified backup blocks the binding.

The binding proves only that a recovery artifact exists for the exact reviewed plan. It does not authorize pair/unpair execution and it does not authorize restore. `execution_authorized`, `restore_execution_authorized`, device-state mutation, infrastructure mutation and external publication remain false.

## HA truthfulness

A verified backup does not turn a single physical USB/serial coordinator into HA. Automatic failover remains unauthorized. HA may only be claimed by a future provider profile after its own failure/recovery qualification.

## Required follow-up

Before 0.65 may claim execution, a later slice must add deliberate provider registration, Identity/RBAC, explicit confirmation, durable Change/Job admission, execution receipt, authoritative read-back, post-condition verification, Audit evidence, restart-safe reconciliation and a typed restore executor whose result is separately verified. Provider acceptance or backup existence alone must never become user-visible success.
