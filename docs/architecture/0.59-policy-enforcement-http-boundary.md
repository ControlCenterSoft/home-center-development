# Home Center 0.59 — Household policy enforcement HTTP boundary

## Scope

This source slice wires the existing qualification-bound Household policy enforcement runtime into the authenticated web process. It remains inside the 0.59 release scope and does not register a concrete provider/backend.

The boundary exposes three explicit POST operations:

- `/api/v1/household/policy/enforcement/plan` — binds the current exact Desired State to a backend identifier and creates a durable plan. The request is bound to `home-center.household-policy-enforcement-plan-request.v1`. The returned plan keeps `backend_mutation_authorized=false`.
- `/api/v1/household/policy/enforcement/confirm` — records an explicit confirmation for the exact plan. The request is bound to `home-center.household-policy-enforcement-confirm-request.v1` and must carry `Idempotency-Key` equal to `plan_id`.
- `/api/v1/household/policy/enforcement/execute` — asks the runtime to perform the already-confirmed plan once. The request is bound to `home-center.household-policy-enforcement-execute-request.v1` and must carry `Idempotency-Key` equal to `plan_id`.

All request contracts are strict Draft 2020-12 JSON schemas with `additionalProperties=false`. The HTTP boundary also performs exact key/schema checks and refuses implicit type coercion before entering the enforcement runtime; the runtime then applies its own identifier and state validation.

All three operations inherit the existing authenticated, first-login, external-access, trusted-proxy and same-origin fences. The enforcement service additionally revalidates Household membership, parent/administration authority and exact Desired State binding before confirmation or execution.

## Fail-closed behavior

Runtime composition creates `HouseholdPolicyEnforcementRuntimeService` with **no adapters registered by default**. Therefore the HTTP execute boundary cannot mutate a backend merely because the route exists. Execution requires a separately registered adapter that satisfies the runtime contract: mutation capability, explicit qualification flag, exact backend identity, version, artifact SHA-256, qualification-evidence SHA-256 and callable apply operation.

A backend invocation is never retried automatically. An ambiguous outcome becomes `in-doubt` and requires read-only reconciliation. Backend acceptance also does not mean verified enforcement: receipts keep `enforcement_verified=false`, `reconciliation_required=true` and `enforcement_success_claim_authorized=false`.

The HTTP boundary does not authorize infrastructure mutation or external publication. It does not introduce a production provider, qualification evidence or any simulated/fallback backend.

## Promotion requirements

Before this slice can be integrated into a release candidate, the integrated exact head still requires normal 0.59 qualification, including request-schema validation, HTTP authorization/origin/error-contract coverage, persistence/restart safety, ambiguous-outcome handling, exact Desired State drift handling, reconciliation linkage, backup/restore preservation, and the full repository security/privacy/infrastructure checks.

Production enforcement additionally remains blocked until a concrete backend adapter is implemented and independently qualified with evidence bound to its exact artifact identity. That external qualification must not be inferred from this source boundary.
