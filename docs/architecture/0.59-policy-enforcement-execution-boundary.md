# Home Center 0.59 — qualification-bound policy enforcement execution boundary

Status: **NR2 source preparation; no PR; no hosted qualification; no production backend registered**.

Baseline: Public Stable 0.56.0. This work remains inside the permitted Stable+3 horizon and belongs only to 0.59. The nearest RC path remains 0.57; this slice does not change RC/Stable or publication status.

## Purpose

Policy Composer already has protected Desired State, read-only Actual State reconciliation, protected verified-state projection and read-only effective-state surfaces. The missing 0.59 boundary is a safe way to issue an exact policy mutation without converting backend acceptance into a false success claim.

This slice introduces a transport-neutral plan → confirm → execute runtime. It deliberately leaves public HTTP wiring and every concrete backend adapter to later qualified work.

## Safety model

The runtime binds one enforcement plan to the exact Household/member, backend id, Desired State generation and originating policy plan, policy id and SHA-256, full Desired State SHA-256, and actor that created the plan.

Planning grants no mutation authority. A separate confirmation step grants only one exact typed backend mutation. Immediately before execution, current Household parent/admin authority and the full Desired State identity are revalidated.

A backend can be registered only when it declares a qualification boundary and supplies content-addressed adapter artifact and qualification-evidence SHA-256 identities. No concrete adapter is registered by this slice.

The adapter receives only the exact composed policy and content-addressed qualification metadata. Secret values are forbidden by contract. Infrastructure mutation and external publication stay false.

## No false success

`apply_policy()` returning `accepted=true` means only that the backend accepted the command. The receipt therefore remains `enforcement_verified=false`, `reconciliation_required=true`, `automatic_retry_authorized=false`, and `enforcement_success_claim_authorized=false`.

The existing read-only reconciliation and verified-state projection must independently prove the post-condition before the effective state can be reported as verified.

If adapter execution raises after invocation, the runtime records an `in-doubt` state and refuses replay. It requires reconciliation instead of automatically repeating a command that may already have been applied.

A rejected command is terminal for that exact execution attempt. A newer retry requires a new explicit plan/confirmation path after reconciliation; this slice never silently retries.

## Deliberate limits

This slice does not register or qualify a concrete production policy backend, expose a new HTTP mutation endpoint, authorize network/filesystem/infrastructure mutation, authorize external publication, claim commercial/legal clearance, claim RC/Stable readiness, or run GitHub Actions.

The next runner-enabled integration must rebase this source onto the then-current 0.59 lane, reconcile any parallel NR1 changes, and run normal exact-head qualification only once.
